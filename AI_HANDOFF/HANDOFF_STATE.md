NOTE: Conceptual design only - zero code change, confirmed by an empty git status on implementation/. No schema, no implementation; the v1.0 contract in code is untouched, and nothing outside its own module consumes it (checked), so v1.1 remains nearly free to land. Decision D-54: a Recommendation is advice from a MLINO engine or module to a role in the business - what should be done, why, grounded in which context and evidence, with what impact and effort - it stays inside V1 and never reaches V2. Required references: at least one KPI, at least one active capability unless the recommendation is itself about developing one, and at least one evidence item; optional references to goals, offers and decisions; kpi_alignment is removed rather than deprecated. Sources are SYSTEM, AI_INFERRED or INTEGRATION; a human never authors a recommendation, because a human plan is a Decision and allowing human authorship would let a manager's own plan be wrapped as MLINO advice, the fabrication D-51 rule 5 forbids. Accepting a recommendation, creating an offer and publishing that offer are three separate acts even when one person performs them, and suggested terms inside a recommendation are proposals, never offer terms. The central finding is a security one, read from the code: v1.0 validation only checks that an evidence kind is a member of EVIDENCE_KINDS, and that list contains "feedback", i.e. customer voice, so customer data can enter the system through a recommendation - a bypass of D-36, which blocked CUSTOMER_DATA "with no bypass"; the business context closed this in D-44 but the recommendation contract had left it open; v1.1 blocks feedback until R8-a. Lifecycle, recorded formally as ADR-0008: draft, proposed, accepted, rejected, expired, superseded. Of the six states the owner proposed for analysis, "Confirmed" was rejected as a state because in MLINO confirmation means human confirmation under ADR-0006, so a machine gate cannot carry the name, and universal human pre-approval would add friction to every recommendation - only a future Policy should require it; "Presented" was rejected as a state because being shown is an event with a timestamp. in_progress and done were removed because after D-51 they duplicated Action.executedAt and a recommendation answered by two actions had no defined "done"; the owner's own proposed lifecycle omitted them too. Rejection now requires a reason from a closed list, and "already_done" links directly to independent actions under D-51, giving a practical moment to prompt recording an unrecorded action. ADR-0008 was written by the criterion established at D-51 - ADR-0005 listed the old statuses in its text, which would otherwise have become silently false; ADR-0005 was not rewritten and received only a second "partially superseded" note. A gap following the OD-31 pattern was found and closed: the approved D-47 edge Decision to Recommendation had no field in v1.0, now covered by decision_refs. An explicit refinement of D-51 rule 4 was made and flagged rather than applied silently: that rule stored authorizedBy on the action because "the recommendation holds no human"; v1.1 changes that premise, so authorizedBy for recommendation-origin actions now defaults to the acceptance recorded on the recommendation, the same logic already used for decision origin. ADR-0007 was not touched because its text never fixed where authorizedBy is stored.
