## ۱. یافته‌های کد

- **جهت import درست است:** هیچ فایل Core از `value-engines/` import نمی‌کند؛ موتورها از Core import می‌کنند.
- **نشت از جنس واژگان است:** Core ماژول را import نمی‌کند، ولی واژگانش را در فهرست‌های بسته نام می‌برد.
- **شِمای Prisma از پیش باز است:** `domainTag` و `intendedAudience` از نوع `String`‌اند ← باز کردن واژگان migration نمی‌خواهد.
- **هیچ جدول نوبت، بیمار، درمان یا درمانگر وجود ندارد** — موتورها از درگاه‌های درون‌حافظه‌ای می‌خوانند.
- **نشت تازه، ثبت‌نشده در OD-39:**
  - `seedV1CoreProducerRegistry` (موتورهای کلینیک درون foundation)
  - `FAMILY_LABELS` در briefing
  - اعتبارسنجی `read-api.ts:111`
  - فهرست مخاطب در `candidate-structural-validator.ts:22`
  - دو نقش سخت‌کد در auth-adapter و درگاه AC-2
- **دقیق‌سازی OD-39:** از چهار برچسب، سه تا کلینیک‌اند و `opportunity.interaction` سازوکار Core است.
- **`event_log` فقط افزودنی است** و زنجیره‌ی تعامل به برچسب رخداد بنیان‌گذار وابسته است ← **برچسب‌های موجود هرگز تغییر نام نمی‌دهند.**

## ۲. D-63 — مرز Core و ماژول

- **آزمون سه‌شرطی Core:** بدون واژگان صنف معنا دارد · Core معنایش را تعریف می‌کند · زنجیره‌ی Core یا دو ماژول مستقل به آن نیاز دارند. **«افقی» ≠ Core**: CRM و حسابداری ماژول‌اند.
- **Core هیچ واژه‌ی صنفی را نام نمی‌برد.** «فرصت» Core است؛ «خانواده‌ی فرصت» مال ماژول است و ثبت می‌شود. **Core هیچ نام نقشی ندارد.**
- **ماژول کلینیک:** نوبت، بیمار، سابقه‌ی درمان، درمانگر (ویژگی و منبع)، موتور ظرفیت، نقش‌های کلینیکی، گردش‌کارهای درمانی.
  - خدمت فروختنی ← توانمندی و آفر Core
  - درمانگر به‌عنوان شخص ← عضو Core
  - رضایت آگاهانه‌ی درمانی ≠ رضایت داده
- **Core «رزرو» عمومی نمی‌سازد.** مفهوم افقی مشترک ← ماژول مشترک.
- **گسترش‌پذیری:** هر شش ماژول در سطح **مفهوم** بدون تغییر Core جا می‌گیرند. در سطح **کد**، هر ماژولی که فرصت یا مخاطب تازه بخواهد پشت یک CCR یک‌باره است.
- **مهاجرت:**
  - م۰: طبقه‌بندی منطقی — همین حالا، بدون کد
  - م۱: یک CCR یک‌باره روی قرارداد منجمد — فهرست بسته ← واژگان ثبت‌شده‌ی فضانام‌دار؛ برچسب‌های موجود حفظ؛ Core اعتبارسنجی می‌کند و تفسیر نمی‌کند
  - م۲: جابه‌جایی کد
- **محافظ:** تا CCR هیچ واژه‌ی صنفی تازه‌ای در Core.

## ۳. D-64 — C-05

- ارکستراسیون تجربه و زیربنای دستیار = **Core**
- رابط دستیار، تطبیق، کشف و رندر = **V2**
- **V1 = Core + ماژول‌ها**
- **خوانش OD-39 من اصلاح شد:** ارکستراسیون تجربه «در سمت V2» نیست؛ V2 فقط رندر می‌کند. جای‌گذاری بافت OD-26 جایگزین شد.
- **محافظ:** خروجی ارکستراسیون برای کاربر نهایی فقط از تصویر منتشرشده (D-52).
- **C-06 (باز، غیرمسدودکننده):** دستیار اعضا روی داده‌ی منتشرنشده کار می‌کند. طبق D-52 نمی‌تواند در V2 باشد، مگر با پالایش D-52.
