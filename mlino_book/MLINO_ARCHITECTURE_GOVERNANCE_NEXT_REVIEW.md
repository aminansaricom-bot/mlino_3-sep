# بازبینی حاکمیت معماری MLINO — گام بعدی پس از D-63 و D-64

**تاریخ:** ۱۱ سپتامبر ۲۰۲۶
**نقش:** بازبین حاکمیت معماری MLINO (Claude Opus 5)
**دامنه:** بازبینی و پیشنهاد — **صفر خط کد، بدون شِما، بدون پیاده‌سازی.** هیچ ADR نوشته نشد و هیچ تصمیم مصوبی تغییر نکرد.

---

## ۰. وضعیت زنده و قواعد این بازبینی

**مخزن پیش از هر نتیجه‌گیری بررسی شد:** همگام با remote (`4910b27`)، درخت کاری تمیز، `HANDOFF_STATE` برابر تحویل OD-40 من. **هیچ عامل دیگری از D-64 به بعد تغییری نداده بود.**

**اصل ماژولار Core** (دستور مالک پس از OD-40) این‌جا **فقط چارچوب اعتبارسنجی** است، **نه جایگزین D-63**. سه پرسش:

- **پ۱.** آیا چند ماژول مستقل به آن نیاز دارند؟
- **پ۲.** آیا بدون هیچ دامنه‌ی کسب‌وکاری معنا دارد؟
- **پ۳.** آیا جزو چرخه‌ی عمر خود پلتفرم است؟

اگر پاسخ هر سه «بله» نباشد، مفهوم در ماژول می‌ماند.

**دامنه‌ی به‌روزرسانی:** خروجی خواسته‌شده فقط همین سند است. **دفتر تصمیم‌ها، CHANGELOG و نقشه‌ی راه دست نخوردند.** ویرایش‌هایی که این بازبینی لازم می‌داند در بند ۶ فهرست شده‌اند و منتظر دستورند.

## ۱. ساختار پیشنهادی ADR — برای D-58 · D-61 · D-62 · D-63 · D-64

**ADRی نوشته نشد.** این‌جا فقط دامنه، عنوان، دلیل و تصمیم‌های هر ADR پیشنهاد می‌شود.

### ۱٫۰ اصلاح در پیشنهاد قبلی خودم

در تحویل OD-40 **دو** ADR پیشنهاد کرده بودم: یکی برای D-58، D-61 و D-62، و یکی برای D-63 و D-64. **حالا سه ADR پیشنهاد می‌کنم:** D-63 و D-64 از هم جدا می‌شوند.

- **دو محور مستقل‌اند.** D-63 محور **Core / ماژول** است و D-64 محور **Core / V1 / V2**. هر کدام می‌تواند بدون دیگری تغییر کند.
- **خوانندگانشان فرق دارند.** D-63 برای نویسندگان ماژول است؛ D-64 برای تیم V2 و طراح دستیار.
- **قاعده‌ی رایج ADR «یک تصمیم، یک ADR» است.** D-58، D-61 و D-62 استثنا می‌مانند، چون هر سه **یک اصل مشترک** را اجرا می‌کنند.

### ۱٫۱ ADR-0010 (پیشنهادی) — «پلتفرم اجرا می‌کند، مجوز نمی‌دهد: سه کانال اختیار، هویت و داده»

| | |
|---|---|
| **دامنه** | مرز بین سه کانالی که هرگز از هم عبور نمی‌کنند: **اختیار** (عضویت، اعطا، بازیابی)، **هویت کسب‌وکار** (راستی‌آزمایی) و **داده** (یکپارچه‌سازی و پیوند)؛ و نقش پلتفرم به‌عنوان مجری، نه منبع اختیار |
| **تصمیم‌های شامل** | **D-58** (بازیابی می‌افزاید و کم نمی‌کند؛ پلتفرم گیرنده را انتخاب نمی‌کند) · **D-61** (راستی‌آزمایی هویت هرگز اختیار حکمرانی نمی‌دهد) · **D-62** (پیوند فقط نگاشت هویت است؛ `ADMIN_ACTION` کانال اجراست؛ رضایت دوطرفه) |
| **چرا ADR لازم است** | ۱. **برگشت‌ناپذیرترین خطاها این‌جاست:** اگر پیاده‌ساز یک بار از `ADMIN_ACTION`، راستی‌آزمایی یا پیوند، اختیار استنتاج کند، مسیر تصاحب کسب‌وکار باز می‌شود. ۲. قاعده‌ی سه ریپو را مقید می‌کند (V1، V2، Content Studio) و امروز فقط در سه ردیف دفتر و سه سند هم‌ترازی پراکنده است. ۳. **محافظ D-62** («ساختن پیوند تا ثبت دو رضایت از هیچ API در دسترس نیست») باید یک قاعده‌ی قابل‌استناد در بازبینی کد باشد، نه یک پاراگراف در سند هم‌ترازی |
| **رابطه با ADRهای موجود** | **ADR-0004 را تایید می‌کند**، جایگزینش نمی‌شود. به ADR-0009 ارجاع می‌دهد |
| **بیرون از دامنه** | جزئیات پنج لایه‌ی بازیابی و فرایند راستی‌آزمایی — در اسناد هم‌ترازی می‌مانند |

### ۱٫۲ ADR-0011 (پیشنهادی) — «Core هیچ واژه‌ی صنفی را نام نمی‌برد»

| | |
|---|---|
| **دامنه** | مرز Core و ماژول‌های دامنه‌ی کسب‌وکار؛ جهت وابستگی؛ الگوی واژگان ثبت‌شده‌ی فضانام‌دار |
| **تصمیم‌های شامل** | **D-63** — با **اصل ماژولار Core** به‌عنوان **چارچوب اعتبارسنجی پیوست** (نه جایگزین آزمون D-63) و بخش واژگان ماژول از **D-62** (عمل‌های فضانام‌دار) |
| **چرا ADR لازم است** | ۱. **این قاعده در بازبینی هر Pull Request اعمال می‌شود:** «آیا این تغییر واژه‌ی صنفی به Core می‌آورد؟» — به یک مرجع ثابت و کوتاه نیاز دارد. ۲. نشت کلینیک **یک بار** اتفاق افتاد چون چنین قاعده‌ای مکتوب نبود. ۳. **ممنوعیت تغییر نام برچسب‌های موجود** (`event_log` فقط افزودنی) در هر بازطراحی آینده وسوسه‌برانگیز است و باید دائمی ثبت شود. ۴. مسیر م۰ ← م۱ ← م۲ و شرط مجوز جداگانه‌ی CCR باید پیش از زمان‌بندی م۱ ثابت باشد |
| **پیش‌شرط نوشتن** | **روشن‌سازی بند ۴٫۲** (قاعده‌ی ۴ در D-63 و یازده دسته‌ی D-55) — بدون آن، ADR یک تعارض را منجمد می‌کند |
| **بیرون از دامنه** | متن CCR م۱ — سند جداگانه با مجوز جداگانه |

### ۱٫۳ ADR-0012 (پیشنهادی) — «سه لایه: Core تعریف می‌کند، V1 حقیقت را نگه می‌دارد، V2 تجربه را می‌سازد»

| | |
|---|---|
| **دامنه** | جای ارکستراسیون تجربه، زیربنای دستیار، رابط دستیار، تطبیق، کشف و رندر؛ قاعده‌ی خروجی ارکستراسیون برای کاربر نهایی |
| **تصمیم‌های شامل** | **D-64** و **مرز Session** (بند ۲، پس از تایید) |
| **چرا ADR لازم است** | ۱. **جای‌گذاری ارکستراسیون دو بار تغییر کرده است:** بافت OD-26 و ردیف D-53 آن را V2 گذاشتند؛ D-64 به دستور صریح مالک آن را Core کرد. بدون ADR، سند قدیمی‌تر دوباره خوانده و اجرا می‌شود. ۲. **خطر نشت داده به V2** — خروجی ارکستراسیون برای کاربر نهایی فقط از تصویر منتشرشده (D-52) — مرزی امنیتی است که تیم V2 باید بدون خواندن ده سند ببیند. ۳. C-06 و Session هر دو روی همین مرز تصمیم گرفته می‌شوند |
| **پیش‌شرط نوشتن** | تصمیم مالک درباره‌ی **C-06**؛ تایید **مرز Session** |
| **بیرون از دامنه** | الگوریتم تطبیق و رتبه‌بندی — مال V2 |

### ۱٫۴ ترتیب پیشنهادی نوشتن

**ADR-0010 اول** — هیچ پیش‌شرطی ندارد و محافظ D-62 را فوراً قابل‌استناد می‌کند. **ADR-0011** پس از روشن‌سازی بند ۴٫۲. **ADR-0012** پس از C-06 و Session. **ADR-0007 تا ADR-0009** هنوز منتظر بازبینی مالک‌اند و این پیشنهاد به آن‌ها دست نمی‌زند.

## ۲. مرز Session

### ۲٫۱ وضعیت امروز — از کد

- **در کتاب MLINO هیچ تصمیم یا تعریفی برای Session وجود ندارد.**
- **در کد، Session به‌عنوان مفهوم وجود ندارد.** آنچه هست یک **JWT بی‌حالت** است (`foundation/auth-adapter/auth-adapter.ts`):
  - سه claim دارد: `organization_id` · `actor_id` · `role`
  - صادرکننده فقط برای تست است (`issueTokenForTesting`)
  - هیچ ذخیره‌گاه Session و هیچ سازوکار لغو ندارد — توکن تا انقضا معتبر است
  - به احراز هویت زنده‌ی Malino وصل نیست (Wave 2+)
  - fail-closed است — بدون `MLINO_JWT_SECRET` کار نمی‌کند
- **هر توکن فقط یک سازمان را حمل می‌کند.** طبق D-57، `organization_id` در توکن **مرجع عضویت نیست**.

### ۲٫۲ آیا Session جزو Core است؟ — **بله**

| پرسش | پاسخ |
|---|---|
| **پ۱ — چند ماژول مستقل؟** | ✅ هر ماژولی که به نمایندگی از یک شخص کار کند |
| **پ۲ — بدون دامنه‌ی کسب‌وکار؟** | ✅ «این شخص الان حاضر و احرازشده است» در کلینیک و رستوران یک معنا دارد |
| **پ۳ — چرخه‌ی عمر پلتفرم؟** | ✅ ورود، تعویض سازمان، انقضا، لغو، بازیابی |

**دلیل ساختاری هم هست:** اگر هر ماژول Session خودش را داشته باشد، **سیستم احراز هویت دوم** عملاً ساخته شده است — همان چیزی که D-62 ممنوع کرد.

### ۲٫۳ تعریف پیشنهادی

**Session = بافت احرازشده و زمان‌دار حضور یک شخص**، به‌همراه حداکثر **یک بافت سازمانی فعال** از طریق یک عضویت.

**Session هیچ‌کدام از این‌ها نیست:** هویت، عضویت، اجازه یا مجوزدهی.

### ۲٫۴ مرز با هویت

| | هویت (Identity) | Session |
|---|---|---|
| **پاسخ به** | «این شخص کیست؟» | «آیا همین شخص **الان** حاضر است؟» |
| **عمر** | پایدار، قابل‌بازیابی (D-58 لایه‌ی ۱) | کوتاه، فاسدشدنی |
| **جهت اشتقاق** | — | **Session از هویت مشتق می‌شود؛ هرگز برعکس** |
| **صادرکننده** | صادرکننده‌ی توکن — **OD-08** | همان صادرکننده، روی هویت |

**قواعد پیشنهادی:**

1. **Session اختیار حمل نمی‌کند.** بافت سازمانی Session فقط می‌گوید شخص **درون کدام سازمان** کار می‌کند. اینکه **چه کاری مجاز است**، هنگام عمل از عضویت و اعطای جاری (D-57) خوانده می‌شود، نه از claim توکن. **پایان عضویت یا لغو اعطا منتظر انقضای Session نمی‌ماند.**
2. **بازیابی هویت همه‌ی Sessionهای موجود آن هویت را پایان می‌دهد.** در غیر این صورت کسی که حساب را ربوده بود، پس از بازیابی هم دسترسی دارد. این **هیچ اعطایی را تغییر نمی‌دهد** (D-58 سالم می‌ماند) — فقط حضور را قطع می‌کند. **نگه‌داشت ایمنی** (D-58) هم می‌تواند Session را ببندد — «فقط بستن».
3. **هیچ Session جانشین.** مدیر پلتفرم نمی‌تواند «به‌جای» عضو یک کسب‌وکار وارد شود — پیامد مستقیم D-55 («مدیر پلتفرم هیچ اجازه‌ی کسب‌وکاری — هرگز») و D-57.
4. **نقش توکن منجمد** (`role`) در Session جدید **مبنای هیچ تصمیمی نیست** — D-55 قاعده‌ی ۱۱. تا CCR م۱ در توکن فعلی می‌ماند.
5. **دسترسی سازمانی (AC-2) می‌ماند.** Session به‌ازای شخص است، ولی **مصرف‌کننده‌ی AC-2 همچنان سازمان است** (D-08). Session نباید AC-2 را به دسترسی فردی تبدیل کند.

### ۲٫۵ مرز با چرخه‌ی عمر دستیار

**گفت‌وگوی دستیار ≠ Session.**

1. **دستیار فقط درون یک Session انسانی فعال عمل می‌کند** و با همان بافت و همان اختیار جاری آن شخص. **هیچ Session یا اعتبارنامه‌ی خودش را ندارد.**
2. **وقتی Session تمام شود، توان دستیار برای عمل هم تمام می‌شود.** کار زمان‌بندی‌شده یا پس‌زمینه‌ی دستیار **نمی‌تواند روی Session ذخیره‌شده اجرا شود** — این همان نیابت ماندگار به ماشین است که D-57 ممنوع کرد. کار پس‌زمینه فقط **پیش‌نویس** می‌سازد (پیشنهاد در وضعیت `draft` — D-54)، نه عمل.
3. **حافظه‌ی گفت‌وگو چرخه‌ی عمر خودش را دارد و Session نیست.**
   - گفت‌وگوی **عضو** ← داده‌ی سازمان، زیر AC-2
   - گفت‌وگوی **کاربر نهایی** ← داده‌ی فردی ← **OD-01**
   - ماندن حافظه پس از Session اختیار نمی‌سازد
4. **دستیار هرگز در مسیر تصمیم حاکمیتی نیست** (D-58). Session او را به آن مسیر وارد نمی‌کند.

### ۲٫۶ Session کاربر نهایی در V2

- **Session کاربر نهایی احرازشده** همان مفهوم Core است، **بدون بافت سازمانی**. پس از هیچ مسیری به داده‌ی منتشرنشده نمی‌رسد (D-52).
- **مرور ناشناس** Session نیست. **حالت تجربه‌ی V2** است: نه اختیار حمل می‌کند نه حقیقت کسب‌وکار.
- **این به C-06 گره می‌خورد:** اگر V2 میزبان Session **با بافت سازمانی** شود، داده‌ی منتشرنشده به V2 می‌رسد. بند ۳٫۳ را ببینید.

### ۲٫۷ آیا ماژول‌ها Session خودشان را می‌سازند؟ — **نه**

- **ماژول Session Core را مصرف می‌کند** و از آن **شخص، بافت سازمانی و عضویت** را می‌گیرد.
- ماژول می‌تواند **حالت محلی و موقت** نگه دارد (مثلاً پیشرفت یک فرم چندمرحله‌ای)، کلیدخورده به Session Core. این **حالت** است، نه Session: نه احراز هویت می‌کند، نه اختیار می‌دهد.
- **واقعیت امروز:** Content Studio ورود و جدول کاربر خودش را دارد. این Session **سیستم بیرونی** است و **V1 هرگز آن را به‌عنوان احراز هویت نمی‌پذیرد** (D-62: سیستم هویت دوم نداریم). حالت نهایی ورود با هویت Core است — وابسته به OD-08.

### ۲٫۸ جمع‌بندی Session — تصمیم پیشنهادی (هنوز ثبت نشده)

**۱.** Session **Core** است — هر سه پرسش را می‌گذراند. **۲.** Session از هویت مشتق می‌شود و **هیچ اختیاری حمل نمی‌کند**؛ اختیار هنگام عمل از عضویت و اعطا خوانده می‌شود. **۳.** بازیابی هویت و نگه‌داشت ایمنی Session را می‌بندند؛ اعطا را تغییر نمی‌دهند. **۴.** Session جانشین برای مدیر پلتفرم وجود ندارد. **۵.** دستیار فقط درون Session انسانی فعال عمل می‌کند؛ کار پس‌زمینه فقط پیش‌نویس می‌سازد. **۶.** ماژول‌ها Session نمی‌سازند؛ حالت محلی ماژول Session نیست. **۷.** Session کاربر نهایی بافت سازمانی ندارد.

**وابستگی اجرا:** OD-08 (صادرکننده‌ی توکن). **مانع تصمیم نیست.** قاعده‌ی ۲ به سازوکار لغو نیاز دارد که امروز در کد نیست. این یک یافته برای پیاده‌سازی است، نه تغییر کد.

## ۳. خطرهای باقی‌مانده‌ی معماری

### ۳٫۱ OD-35 — جای آفر در طبقه‌بندی دانش · **خطر: کم**

- **آزمون Core:** آفر هر سه پرسش را می‌گذراند (همه‌ی ماژول‌های فروشنده؛ سه شکل عمومی قلم، بسته و کمپین در D-53؛ چرخه‌ی انتشار). **آفر Core است**؛ این در OD-35 محل بحث نیست.
- **پرسش باز فقط شکل است:** نوع دانش دوازدهم (فهرست یازده‌تایی مصوب D-31)، یا موجودیت تجاری با همان چهار بُعد.
- **اثر ماژول‌ها:** کاتالوگ صنفی (منو، بسته‌ی درمان) در هر دو گزینه واژگان ماژول است روی شکل‌های عمومی. **D-63 روی هیچ‌کدام از دو گزینه اثر نمی‌گذارد.**
- **خطر واقعی:** پیاده‌سازی آفر پیش از بستن OD-35 ← دو نمایش از یک مفهوم. **محافظ موجود کافی است:** آفر پس از بُعد شاهد فاز ۲ پیاده می‌شود. **OD-35 باید پیش از آن گام بسته شود.**

### ۳٫۲ OD-07 — یادگیری بین کسب‌وکارها · **خطر: بالا در بلندمدت، غیرفعال امروز**

**بزرگ‌ترین مسیر آینده برای بازگشت واژگان صنفی به Core** — و هم‌زمان مسیر نشت حریم خصوصی. چهار خطر:

| خطر | توضیح | محافظ |
|---|---|---|
| **حریم خصوصی** | داده‌ی یک کسب‌وکار روی کسب‌وکار دیگر اثر می‌گذارد | **OD-01** — وابستگی ثبت‌شده |
| **علیت قضاوت‌نشده** | تجمیع ارزیابی‌های بی‌انتساب | D-50 (اثربخشی ≠ انتساب) |
| **نشت واژگان** | «کلینیک‌هایی که عدم‌حضور را ظرف دو ساعت پیگیری می‌کنند…» **دانش صنفی** است | **پیامد D-63:** سازوکار تجمیع = Core؛ **محتوای بینش = فضانام ماژول** — تجمیع فقط درون واژگان یک ماژول |
| **نشت رقابتی** | بینش یک کلینیک به رقیب هم‌محله‌اش سود می‌رساند | رضایت سازمان (D-08: رضایت وقتی داده از سازمان خارج می‌شود) |

**کد امروز:** تنها جدول تجمیعی (`RevenueRecoveryRawAggregate`) با `organizationId` کلید می‌خورد — **تجمیع درون یک سازمان است، نه بین سازمان‌ها.** ✅

**محافظ پیشنهادی بدون کد:** **هیچ تجمیع بین‌سازمانی** پیش از بستن OD-07 ساخته نشود.

### ۳٫۳ C-06 — رابط دستیار اعضای کسب‌وکار · **خطر: متوسط، غیرمسدودکننده**

- **مسئله:** «رابط دستیار = V2» (D-64) برای کاربر نهایی درست است. دستیار **عضو** روی حقیقت منتشرنشده کار می‌کند و D-52 آن را از V2 دور نگه می‌دارد.
- **پیوند تازه با Session (بند ۲٫۶):** میزبانی رابط دستیار عضو در V2 یعنی V2 **Session با بافت سازمانی** نگه دارد. این همان نقطه‌ای است که D-52 شکسته می‌شود.
- **خوانش من بدون تغییر:** سطوح عضو پشت AC-2 می‌مانند. اگر V2 سطح احراز‌هویت‌شده‌ی اعضا هم شود، پالایش صریح D-52 لازم است.
- **زمان تصمیم:** **پیش از ساختن هر رابط دستیار برای اعضا.** تا آن زمان هیچ کاری را متوقف نمی‌کند.

### ۴٫۱ روش

هر ردیف با متن دفتر تصمیم‌ها و — جایی که ادعا به کد برمی‌گشت — با کد مقایسه شد (`auth-adapter.ts`، `recommendation-contract.ts`، `schema.prisma`). ادعایی از حافظه نیامده است.

### ۴٫۲ ⚠️ تنش: قاعده‌ی ۴ در D-63 و یازده دسته‌ی D-55

**آنچه D-63 نوشت:** «Core **هیچ نام نقشی** ندارد. واژگان نقش و مخاطب را ماژول تامین می‌کند.» در جدول بند ۲٫۲: «واژگان نقش مال ماژول است — Core هیچ نام نقشی ندارد».

**آنچه D-55 مصوب کرد (قاعده‌ی ۱۱):** **یازده دسته** — `owner_founder` · `executive` · `general_manager` · `operations_manager` · `marketing` · `sales` · `customer_service` · `finance` · `hr` · `specialist` · `custom_role` — «زبان مشترک MLINO» برای **مسیریابی و یادگیری**، که «به ماژول خنثی می‌روند». این دسته‌ها **امروز در کدند:** `TARGET_ROLES` در `foundation/recommendation/recommendation-contract.ts:42`.

**اگر قاعده‌ی ۴ لفظی خوانده شود،** این یازده دسته از Core بیرون می‌روند و مسیریابی پیشنهاد (`target_role`) به ماژول وابسته می‌شود. **این D-55 را تضعیف می‌کند.**

**چرا به نظرم تعارض واقعی نیست:**
- **دسته ≠ نقش.** D-55 خودش جدا کرده است: نقش **نام کسب‌وکار** است («پذیرش»، «دندان‌پزشک»)، و هر نقش **به یکی از یازده دسته نگاشت می‌شود**.
- **یازده دسته هر سه پرسش را می‌گذرانند:** همه‌ی ماژول‌ها به مسیریابی مسئولیت نیاز دارند؛ هیچ‌کدام صنفی نیست — دندان‌پزشک به `specialist` نگاشت می‌شود؛ مسیریابی پیشنهاد و اقدام جزو چرخه‌ی عمر پلتفرم است.
- **هدف قاعده‌ی ۴** در متن D-63 **نام‌های نقش صنفی** بود (`receptionist_coordinator`، منشی، درمانگر).
- **«ماژول خنثی» در D-55 یعنی واحد کد مشترک**، نه ماژول دامنه‌ی کسب‌وکار به معنای D-63. **واژه‌ی «ماژول» در دو معنا به کار رفته است.**

**خوانش پیشنهادی:** قاعده‌ی ۴ یعنی «Core هیچ **نام نقش** — نام کسب‌وکار یا نقش صنفی — ندارد». **یازده دسته‌ی مسئولیت D-55 واژگان مستقل از دامنه‌ی Core‌اند و در Core می‌مانند.** نه D-55 تغییر می‌کند، نه D-63.

**چرا خودم ثبتش نکردم:** D-63 تصمیم ثبت‌شده است و این دستور تغییر تصمیم را منع کرده. **تایید یک‌خطی مالک لازم است** ← حکم B.

### ۴٫۳ ثبت ناقص: ردیف D-53

ردیف D-53 می‌گوید: «V2 تطبیق، نمایش **و ارکستراسیون**». D-64 به دستور صریح مالک ارکستراسیون تجربه را **Core** کرد. در تحویل OD-40 نوشتم «جای‌گذاری بافت OD-26 جایگزین شد»، **ولی ردیف D-53 — که همان تصمیم OD-26 است — یادداشت ارجاع به D-64 نگرفت.**

**هسته‌ی D-53 سالم است:** آفر مال V1 است؛ V2 هرگز آفر نمی‌سازد و شرایط را عوض نمی‌کند. فقط یک واژه به‌روز نیست. **یک یادداشت در دفتر لازم است** — تصمیم تازه‌ای نمی‌خواهد.

### ۴٫۴ یک ارجاع نادقیق در سند OD-40 خودم

در جدول بند ۲٫۲ سند `OD-40_CORE_MODULE_BOUNDARY_ALIGNMENT.md`، مرجع «هویت» **D-11 · D-62** نوشته شده است. **D-11 درباره‌ی نگاشت Content Studio است**، نه هویت. ربطش فقط از مسیر D-62 است («سازگار با D-11»). مرجع درست D-62 و OD-08 است. **هیچ تصمیمی تضعیف نمی‌شود.**

## ۵. حکم: **B — روشن‌سازی جزئی لازم است**

**تنها مانع مشخص:**

**۱. تایید خوانش قاعده‌ی ۴ در D-63** (بند ۴٫۲): «Core هیچ **نام نقش** صنفی یا کسب‌وکاری ندارد؛ **یازده دسته‌ی مسئولیت D-55 در Core می‌مانند**.»

بدون این تایید، پیاده‌سازی که D-63 را لفظی بخواند ممکن است `TARGET_ROLES` را از Core بیرون ببرد. ADR-0011 هم نباید پیش از آن نوشته شود.

**این‌ها مانع نیستند:**
- **یادداشت D-53** و **اصلاح ارجاع D-11** — ویرایش ثبت، نه تصمیم؛ منتظر دستوری که ویرایش دفتر را مجاز کند.
- **مرز Session** — تصمیم پیشنهادی آماده است و برای ثبت منتظر تایید شماست. اجرا وابسته به OD-08 است.
- **C-06** — تصمیمش پیش از ساختن رابط دستیار اعضا لازم است.
- **OD-35** — پیش از پیاده‌سازی آفر لازم است.
- **OD-07** — به OD-01 وابسته است؛ محافظ «بدون تجمیع بین‌سازمانی» کافی است.

**با این تایید، بستن معماری ادامه می‌یابد (A).**
