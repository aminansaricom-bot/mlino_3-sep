# نقشه‌ی راه اتصال

**تاریخ:** ۹ سپتامبر ۲۰۲۶ · **بازنگری:** پس از تصمیم مالک (بند ۱۰)
**اصل حاکم:** `Reuse → Wrap → Integrate → Consolidate (فقط با توجیه)`

---

## ⚠️ تغییر ترتیب نسبت به نسخه‌ی قبلی — ثبت صریح تعارض

نسخه‌ی ۰٫۱ این سند **اتصال موتورهای فرصت به Postgres را گام ۲** گذاشته بود، پیش از نهایی شدن قراردادها. استدلالم این بود که آن گام بیشترین ارزش را با کمترین ریسک دارد.

**مالک محصول این ترتیب را رد کرد** و ترتیب زیر را تصویب کرد:

```
۱ قرارداد مشترک پیشنهاد  →  ۲ نگاشت سازمان  →  ۳ اتصال دیتابیس  →  ۴ لایه‌ی API  →  ۵ رابط کاربری
```

با این قاعده: **«دیتابیس نباید پیش از قراردادها طراحی شود.»**

**چرا تصمیم مالک درست است:** اگر Repository‌ها پیش از تثبیت قرارداد به دیتابیس وصل شوند، شکل ذخیره‌سازی بر اساس مدل داخلی امروز شکل می‌گیرد، نه بر اساس مفهوم مشترک. آن‌وقت مهاجرت بعدی گران‌تر از تأخیر امروز است. مخصوصاً که ممیزی نشان داد سه مفهوم اجباری قرارداد (`target_role`، `expected_impact`، `effort`) در **هیچ‌کدام** از دو موتور وجود ندارند — یعنی شِمای امروز ناقص است و نباید مبنای جدول‌سازی شود.

این تعارض در `05_OPEN_DECISIONS.md` هم به‌عنوان D-09 ثبت شده و بی‌صدا حل نشده.

## گام ۱ — قرارداد مشترک پیشنهاد ✅ **IMPLEMENTED / VALIDATED**

**چه:** تثبیت شِمای `Recommendation` به‌عنوان تعریف canonical در V1. فقط تعریف نوع — بدون ذخیره‌سازی، بدون مصرف‌کننده، بدون تغییر رفتار.

**چرا اول:** هر تصمیم بعدی — از شکل جدول تا شکل API — از این تعریف مشتق می‌شود.

**آنچه اینجا حل می‌شود:** تعریف نقش‌ها (برای `target_role`)، تعریف `owner`، و مقیاس `expected_impact` و `effort`. این‌ها تصمیم محصولی‌اند، نه فنی.

**انجام شد.** `foundation/recommendation/` — تعریف نوع + راستی‌آزمایی fail-closed، ۳۱ تست، مجموع Suite ‏۱۹۳/۱۹۳، `tsc` پاک، build موفق، **هر دو فایل منجمد دست‌نخورده**.

سه مفهومی که در گام ۱ باید تصمیم‌گیری می‌شد، تصمیم‌گیری شد: یازده نقش، هشت نوع × چهار سطح اثر، و مقیاس زمانی effort.

## گام ۲ — نگاشت `workspace ⇄ organization` ✅ **IMPLEMENTED / VALIDATED**

**چه:** پیاده‌سازی `ExternalWorkspaceLink` و رابط resolve، طبق قرارداد A و ADR-0004.

**قید مصوب:** **هیچ تغییر دیتابیسی در Content Studio** فقط برای افزودن `organization_id`. نگاشت یک‌طرفه در V1 زندگی می‌کند.

**انجام شد.** CCR ‏**APPROVED** · `ExternalWorkspaceLink` + migration `20260910020000` + `foundation/workspace-link/` · ۱۷ تست · مجموع Suite ‏۲۱۰/۲۱۰ · `tsc` پاک · build موفق.

ناوردای «حداکثر یک پیوند فعال» با **ایندکس یکتای جزئی در خودِ دیتابیس** اجبار می‌شود — نه با بررسی اپلیکیشنی. یک تست این را با دور زدن کامل لایه‌ی سرویس اثبات می‌کند.

**باقی‌مانده:** اجرای سیاست حذف `workspace` عمداً موکول شد → OD-12

## گام ۳ — اتصال دیتابیس

**چه:** جایگزینی سه Repository در حافظه (`cancellation`، `capacity`، `followup`) با پیاده‌سازی واقعی روی Postgres، **با شِمایی که از قرارداد گام ۱ مشتق شده**.

**چرا اینجا و نه زودتر:** این بزرگ‌ترین شکاف بین وضعیت فعلی و چشم‌انداز است و بیشترین ارزش را دارد — ولی شکل ذخیره‌سازی باید از مفهوم مشترک بیاید، نه از مدل داخلی امروز.

**پیش‌نیاز:** گام ۱ ✅ و گام ۲ · **ریسک:** متوسط — منطق تشخیص دست‌نخورده می‌ماند، فقط لایه‌ی ذخیره‌سازی عوض می‌شود
**ارزش مستقل:** ✅ V1 برای اولین بار فرصت واقعی از داده‌ی واقعی تولید می‌کند

## گام ۵ — رابط کاربری: موتور اقدام روزانه

**چه:** نمای واحد اقدام روزانه، گروه‌بندی‌شده بر اساس نقش. اینجا بند ۳ چشم‌انداز برای اولین بار واقعاً کار می‌کند.

**قید مصوب (بند ۷ دستور):** این **داشبورد نیست**. هر اقدام باید دلیل، مسئول، اثر انتظاری، KPI مرتبط و نتیجه‌ی قابل‌اندازه‌گیری داشته باشد. اگر یکی از این‌ها نباشد، آن مورد اصلاً نمایش داده نمی‌شود.

**تصمیم باز:** رتبه‌بندی بین‌منبعی (OD-06). تا تعریف نشود، فقط گروه‌بندی می‌شود.

## گام ۶ — Business Context / Business Brain

**طراحی انجام شد** → [`contracts/BUSINESS_CONTEXT_MODEL.md`](contracts/BUSINESS_CONTEXT_MODEL.md) — دوازده موجودیت، مدل منشأ، مدل تازگی و اطمینان. **بدون شِما، بدون کد.**

**فاز ۱ انجام شد ✅** — قراردادهای دامنه‌ی `Fact` · `Goal` · `KPI` · `Capability` در `foundation/business-context/`، ۳۹ تست، مجموع Suite ‏۲۴۹/۲۴۹. **بدون شِمای دیتابیس** — طبق قید صریح: اول قرارداد دامنه.

**فاز ۲ — طراحی مصوب شد، در انتظار بازبینی مستندات:** `Observation` · `Evidence` · `Signal` · `Decision` → [`contracts/BUSINESS_CONTEXT_PHASE2_DESIGN.md`](contracts/BUSINESS_CONTEXT_PHASE2_DESIGN.md)

پنج تصمیم بازبینی اعمال شد (D-39 تا D-43): منبع `AI_INFERRED` برای `Observation` رد شد · `Evidence` مفهوم مستقل شد و به قرارداد پیشنهاد وصل نمی‌شود · `Goal.createdByDecision` اختیاری تصویب شد · تفکیک `strength` از `strengthBasis` تصویب شد · تصمیم سیستم بیرونی بیرون از V1 ماند.

چهار تصمیم تکمیلی هم اعمال شد (D-44 تا D-47): `Evidence` **پشتیبان** ادعاهای دانش است و **جایگزین `Observation` نیست** · `Evidence` **نوع دانش نیست** و `KNOWLEDGE_TYPES` دست‌نخورده می‌ماند · `AI_INFERRED` **نمی‌تواند شاهد بسازد** · C-02 با دو منظر معتبر بسته شد.

```
ساختار نهایی    Knowledge Item + Evidence + Provenance + Confirmation
جریان عملیاتی   Observation → Signal → Decision → Recommendation
حلقه‌ی یادگیری   Evaluation → Decision آینده
```

**همچنان صفر خط کد** — بدون شِما، بدون migration، بدون Repository، بدون integration، بدون ADR جدید. **هیچ تصمیم باز جدیدی ایجاد نشد.**

**حلقه‌ی دانش هم‌تراز شد ✅** (OD-30 → D-48) → [`contracts/KNOWLEDGE_LOOP_ALIGNMENT.md`](contracts/KNOWLEDGE_LOOP_ALIGNMENT.md) — `Reality` مرز است، `Knowledge` لایه‌ی دانش پایدار، `Learning` فرایند. **هیچ موجودیت جدیدی لازم نشد.**

**فاز ۳:** تکامل دانش، یادگیری، استنتاج — یعنی همان فرایند `Learning`. حلقه‌ی یادگیری هم‌تراز شد ✅ (OD-31 → D-49) → [`contracts/LEARNING_LOOP_ALIGNMENT.md`](contracts/LEARNING_LOOP_ALIGNMENT.md). مدل ارزیابی هم‌تراز شد ✅ (OD-32 → D-50) → [`contracts/EVALUATION_MODEL_ALIGNMENT.md`](contracts/EVALUATION_MODEL_ALIGNMENT.md) — اثربخشی جدا از انتساب. **قرارداد پیشنهاد v1.1** = OD-27 (در انتظار) + D-50 — یک بازنگری، پیش از گام ۳. مدل اقدام هم‌تراز شد ✅ (OD-33 → D-51 · ADR-0007) → [`contracts/ACTION_MODEL_ALIGNMENT.md`](contracts/ACTION_MODEL_ALIGNMENT.md) — اقدام مستقل، پیشنهاد یکی از مبدأها. **هر سه پیش‌نیاز مدل‌سازی حلقه‌ی یادگیری (OD-31 · OD-32 · OD-33) بسته شدند.** قرارداد پیشنهاد v1.1 = OD-27 (در انتظار) + D-50 + D-51.

⛔ **شروع نمی‌شود:** ذخیره‌سازی دیتابیس · یکپارچه‌سازی پیشنهاد · پیاده‌سازی داده‌ی مشتری

**پیش‌نیاز ذخیره‌سازی:** CCR فازی طبق OD-17 (تصویب‌شده به‌عنوان راهبرد)
**نکته:** بدون این، `objective` در قرارداد پیشنهاد همیشه خالی می‌ماند.
