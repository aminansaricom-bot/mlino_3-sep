## ۲. تصمیم جداسازی مستأجر — RR2

### ۲٫۱ تایید: **کلیدهای خارجی مرکب، محدود به سازمان، برای موجودیت‌های وابسته به مستأجر**

**قاعده:**
- هر جدول وابسته به مستأجر یکتای **`(id, organization_id)`** دارد.
- هر ارجاع درون‌مستأجری با **کلید خارجی مرکب** `(x_id, organization_id)` بسته می‌شود.
- پس دو سر هر رابطه **در خود دیتابیس** مال یک سازمان‌اند.

**مبنای مصوب:**
- **D-08** — مصرف‌کننده‌ی AC-2 = سازمان
- **D-57** — اعطا درون عضویت یک سازمان
- **پیش‌نمونه‌ی پروژه:** ناوردای امنیتی «در خود دیتابیس، نه با بررسی اپلیکیشنی» — `ExternalWorkspaceLink` · D-61

### ۲٫۲ دامنه‌ی اعمال

| موجودیت | `organization_id` | ارجاع‌های مرکب لازم |
|---|---|---|
| `Organization` | — ریشه | — |
| `BusinessIdentityClaim` | ✅ | — |
| `IdentityVerification` | **افزوده شود** | ← ادعا |
| `BusinessProfile` | ✅ | ← ادعا (بند ۴) |
| `Membership` | ✅ | — |
| `PermissionGrant` | **افزوده شود** | ← عضویت دریافت‌کننده · ← `granted_by` عضویت |
| `Capability` | ✅ | ← `confirmed_by` عضویت |
| `Offer` | ✅ | — |
| `OfferVersion` | **افزوده شود** | ← آفر |
| `OfferVersionCapability` | **افزوده شود** — امروز ندارد | ← نسخه · ← توانمندی |
| `Evidence` | ✅ | ← توانمندی **یا** نسخه · ← `confirmed_by` عضویت |
| `Publication` | ✅ | ← پروفایل **یا** توانمندی **یا** نسخه · ← `performed_by` عضویت · ← اعطا (YR2) |

**بیرون از قاعده:** `reviewed_by_platform_identity_ref` — **عمداً** مستأجری نیست. بازبین پلتفرم عضو کسب‌وکار نیست (ADR-0010 · D-55).

### ۲٫۳ دو نکته‌ی امکان‌پذیری

**(الف) ارجاع‌های اختیاری و XOR — در PostgreSQL کار می‌کند.**
- کلید خارجی مرکب با پیش‌فرض `MATCH SIMPLE` وقتی **یکی** از ستون‌ها تهی باشد **بررسی نمی‌شود.**
- پس `capability_id` تهی + `organization_id` پر = بدون بررسی (درست، شاخه‌ی دیگر XOR)؛ `capability_id` پر = بررسی کامل. ✅

**(ب) Prisma — باید با یک آزمون کوچک راستی‌آزمایی شود.**
- Prisma رابطه‌ی مرکب (`fields: [...]`, `references: [...]`) و `@@unique([id, organizationId])` را پشتیبانی می‌کند.
- ولی **رابطه‌ی اختیاری با ستون‌های نیمه‌اجباری** — `organizationId` اجباری، `capabilityId` اختیاری — ممکن است در Prisma محدودیت داشته باشد.
- **در این یادداشت ادعای قطعی نمی‌شود.** اگر محدودیت بود، **همان پیش‌نمونه‌ی `20260910020000`** به کار می‌آید: کلید خارجی مرکب با **SQL دستی** در migration.
- **این آزمون، اولین گام پیاده‌سازی است.**

## ۴. مالکیت `BusinessProfile` — تحلیل سه گزینه

**قیدهای مصوب که هر گزینه باید رعایت کند:**
- **D-61:** یک سازمان **چند** ادعا (شعبه‌ها)؛ هر ادعا فقط مال یک سازمان؛ حداکثر یک ادعای فعال راستی‌آزمایی‌شده برای هر کسب‌وکار واقعی؛ **ساختن سازمان ≠ ادعای هویت**
- **D-52 · D-61:** انتشار پیش‌شرط **ادعای راستی‌آزمایی‌شده‌ی فعال** دارد
- **D-71 · ADR-0011:** داده‌ی عمومی در Core؛ V2 به ماژول وابسته نیست
- **D-56:** ساعت کاری = `Fact` اعلام‌شده، نه دسترس‌پذیری
- **طرح نسخه‌ی ۲:** ادعای پس‌گرفته یا منقضی **دوباره فعال نمی‌شود** — «ادعای تازه رکورد تازه است»

### ۴٫۱ مقایسه

| معیار | **الف — سطح سازمان** (طرح نسخه‌ی ۲) | **ب — سطح ادعای هویت** | **ج — موجودیت جدای مکان یا شعبه** |
|---|---|---|---|
| **شکل** | یک پروفایل به‌ازای سازمان — یکتای `organization_id` | یک پروفایل به‌ازای ادعا — یکتای `claim_id` | چند مکان به‌ازای سازمان؛ هر مکان به ادعایی ارجاع می‌دهد |
| **شعبه‌ها (D-61)** | ❌ یک مکان برای همه‌ی شعبه‌ها — بعداً migration | ✅ | ✅ |
| **«کدام ادعا؟» در دروازه‌ی انتشار** | ❌ مبهم — پروفایل ارجاع به ادعا ندارد | ✅ روشن | ✅ روشن |
| **تجدید ادعا** (ادعای تازه = رکورد تازه) | ✅ اثری ندارد | ❌ **پروفایل به رکورد مرده بسته می‌شود** — باید منتقل یا کپی شود | ✅ فقط ارجاع مکان به ادعای تازه عوض می‌شود |
| **پیش‌نویس پیش از راستی‌آزمایی** — D-61: ساختن آزاد | ✅ | ❌ ادعا باید اول وجود داشته باشد | ✅ ارجاع ادعا تا راستی‌آزمایی تهی |
| **جفت‌شدن داده‌ی نمایشی با چرخه‌ی راستی‌آزمایی** | ✅ جدا | ❌ **ادعا یک مصنوع راستی‌آزمایی است، نه چهره‌ی عمومی** | ✅ جدا |
| **پیچیدگی MVP** | کمترین | کم | **کم — اگر همان `BusinessProfile` نقش مکان را بازی کند** |

### ۴٫۲ توصیه: **ج در شکل حداقلی — `BusinessProfile` خودش واحد مکان یا شعبه است**

**موجودیت تازه‌ای افزوده نمی‌شود. فقط سه تغییر در `BusinessProfile` طرح نسخه‌ی ۲:**

| تغییر | چرا |
|---|---|
| **حذف یکتای `organization_id`** | شعبه‌ها بدون migration |
| **افزودن ارجاع `business_identity_claim_id`** — **تهی تا راستی‌آزمایی**؛ یکتای جزئی وقتی پر است — با کلید مرکب بند ۲ | «کدام ادعا؟» روشن؛ پیش‌نویس آزاد (D-61)؛ تجدید ادعا = عوض کردن ارجاع |
| **مکان: طول و عرض جغرافیایی عددی** به‌جای jsonb (YR4-ج) | پرس‌وجوی «نزدیک من» در V2 |

**قاعده‌ی MVP:** «**یک پروفایل برای هر سازمان**» به‌عنوان **قاعده‌ی دامنه**، **نه** قید دیتابیس. دمو شعبه ندارد؛ مدل اجازه‌اش را دارد.

**دروازه‌ی انتشار پروفایل:** `business_identity_claim_id` پر · آن ادعا **راستی‌آزمایی‌شده و فعال** · پروفایل `ACTIVE` · فیلدهای عمومی MVP پر.

**آزمون Core برای «پروفایل به‌عنوان مکان»:**
- ✅ همه‌ی صنف‌ها مکان دارند
- ✅ بدون واژه‌ی صنفی
- ✅ جزو چرخه‌ی کشف پلتفرم

**مفهوم تازه‌ی Core نیست** — تحقق داده‌ای «شعبه‌ها»ی D-61 است.

### ۴٫۳ یک تصمیم باز مالک — مانع Prisma نیست

**اجازه‌ی انتشار پروفایل** در شش اجازه‌ی حداقلی D-57 نیست (YR4-ب). چون `permission_key` **رشته‌ی ثبت‌شده** است، این تصمیم **روی شِما اثری ندارد** — فقط Registry.

**باید پیش از پیاده‌سازی قابلیت انتشار پروفایل تصمیم شود** — ذیل OD-05:
- یک عمل Core تازه در خانواده‌ی «رضایت انتشار» (D-55) — **پیشنهاد**
- یا نگاشت صریح به یک اجازه‌ی موجود
