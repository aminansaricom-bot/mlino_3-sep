## ۳. آزمون‌های سازگاری انتشار (PC)

### ۳٫۱ سازوکار زیر آزمون — و یک اصلاح پیشنهادی

**سازوکار مبنا** (سند حل موانع §۵٫۲ · طراحی C15):
- **Trigger A** — `AFTER INSERT` روی `publications`: projection هدف را به‌روز می‌کند.
- **Trigger B** — `BEFORE UPDATE` روی هر هدف: تغییر مستقیم `publication_status`، `published_content_revision` و `published_at` را رد می‌کند، مگر وقتی از مسیر Trigger A آمده باشد.

**⚠️ یافته‌ی ۱ — نشت پرچم:**
- سند حل موانع می‌گوید Trigger B «فقط تغییر نشانه‌گذاری‌شده از مسیر Publication Trigger در همان تراکنش» را بپذیرد.
- اگر نشانه با `set_config('mlino.x', 'on', true)` گذاشته شود، **تا پایان تراکنش** باقی می‌ماند.
- پس این توالی **پذیرفته می‌شود**:

```text
BEGIN
  INSERT publication(...)                          -- پرچم روشن می‌شود
  UPDATE offer_versions SET publication_status = 'PUBLISHED' WHERE id = <نسخه‌ی دیگر>
                                                   -- پرچم هنوز روشن است → پذیرفته
COMMIT
```

**دو جایگزین که باید آزموده شوند:**

| گزینه | سازوکار | خطر |
|---|---|---|
| **B1 — پیشنهاد اول** | Trigger B فقط وقتی اجازه می‌دهد که **`pg_trigger_depth() > 1`** باشد — یعنی UPDATE از **درون** یک Trigger دیگر آمده است | هیچ وضعیت ماندگاری ندارد، پس نشتی نیست. خطر: Trigger دیگری در آینده روی همین ستون‌ها بنویسد — با فهرست بسته‌ی Triggerها کنترل می‌شود |
| B2 | همان پرچم، ولی Trigger A **بلافاصله پس از UPDATE** آن را خاموش کند | خطای نیمه‌راه ممکن است پرچم را روشن بگذارد؛ رفتار زیر Savepoint باید آزموده شود |

**معیار انتخاب:** گزینه‌ای که **PC-04 و PC-05** را بگذراند. اگر هر دو بگذرانند، **B1** — ساده‌تر و بدون وضعیت.

**⚠️ اصلاح پیشنهادی ۲ — اعتبار گذار در Trigger A.** Trigger A فقط projection را نمی‌نویسد؛ **گذار را هم بررسی می‌کند** و **ردیف هدف را قفل می‌کند** (`SELECT … FOR UPDATE`):

| رخداد | هدف | شرط پذیرش |
|---|---|---|
| `WITHDRAWN` | همه | وضعیت فعلی هدف `PUBLISHED` است |
| `PUBLISHED` | OfferVersion | وضعیت فعلی `PUBLISHED` **نیست** |
| `PUBLISHED` | Profile · Capability | وضعیت فعلی `PUBLISHED` نیست، **یا** `content_revision` رخداد از `published_content_revision` فعلی بزرگ‌تر است (انتشار دوباره‌ی بازبینی تازه) |
| `PUBLISHED` | Profile · Capability | **`content_revision` رخداد = `content_revision` فعلی هدف** — رخداد نمی‌تواند بازبینی‌ای را منتشر کند که وجود ندارد |
| همه | همه | هدف، عضو انجام‌دهنده و رخداد هم‌سازمان‌اند — FK مرکب هم این را تضمین می‌کند؛ اینجا دفاع دوم است |

**بدون این بررسی، رخدادهای تکراری یا بی‌معنا وارد تاریخچه‌ی فقط‌افزودنی می‌شوند و دیگر پاک‌شدنی نیستند** (PC-09 و CT-01).

## ۴. آزمون‌های رفتار کلید خارجی (FK)

**سیاست زیر آزمون** (سند حل موانع §۳، FY1):
- همه‌ی FKها `ON DELETE RESTRICT` و `ON UPDATE RESTRICT`
- بدون `CASCADE` و `SET NULL`
- حذف فیزیکی جدول‌های تاریخی ممنوع

### ۴٫۱ یافته‌ی ۲ — `MATCH SIMPLE` و زوج سایه

- پیش‌فرض PostgreSQL برای FK مرکب **`MATCH SIMPLE`** است: اگر **هر یک** از ستون‌ها تهی باشد، FK **اصلاً بررسی نمی‌شود.**
- پس ردیفی با `capability_id = '<شناسه‌ی ناموجود>'` و `capability_organization_id = NULL` **از FK عبور می‌کند.**
- **تنها چیزی که جلویش را می‌گیرد CHECK C6 است.**

| گزینه | سازوکار |
|---|---|
| **فقط C6** (طراحی فعلی) | CHECK: هر دو تهی یا هر دو پر و برابر `organization_id` |
| **C6 + `MATCH FULL`** (پیشنهاد P1) | FK خودش زوج نیمه‌پر را رد می‌کند؛ C6 فقط برابری سازمان را بررسی می‌کند. **دفاع دولایه.** Prisma `MATCH FULL` را بیان نمی‌کند → SQL دستی |

**FK-05 هر دو را می‌آزماید** و نشان می‌دهد چرا C6 **اختیاری نیست.**

### ۴٫۲ فهرست آزمون

## ۵. آزمون‌های یکتایی ادعای هویت (ID)

**قید زیر آزمون — C1:**

```sql
CREATE UNIQUE INDEX business_identity_claim_active_identifier_unique
  ON business_identity_claims (identifier_type, identifier_value)
  WHERE claim_status IN ('VERIFIED', 'SUSPENDED');
```

| # | سناریو | انتظار |
|---|---|---|
| **ID-01** | دو سازمان، یک `(type, value)`، هر دو `VERIFIED` | دومی `23505` |
| **ID-02** | الف `SUSPENDED`، ب تلاش برای `VERIFIED` | `23505` — **تعلیق شناسه را آزاد نمی‌کند** (F3) |
| **ID-03** | چند ادعای `PENDING` از چند سازمان روی یک شناسه | **پذیرفته** — رقابت فقط در لحظه‌ی راستی‌آزمایی قطع می‌شود |
| **ID-04** | الف `REJECTED` یا `EXPIRED`، سپس ب `VERIFIED` | پذیرفته |
| **ID-05** | یک `value` با دو `identifier_type` متفاوت | پذیرفته — دو شناسه‌ی متفاوت معادل نیستند (طراحی §۴٫۲) |

## ۶. آزمون‌های هم‌زمانی تراکنش (CT)

### ۶٫۱ روش

- **دو اتصال مستقل** (Node + `pg`، بدون Pool مشترک).
- هر آزمون یک **توالی قطعی** دارد: گام‌ها با **Advisory Lock** به‌عنوان مانع هماهنگ می‌شوند (`pg_advisory_lock` / `pg_advisory_unlock` روی کلید آزمون) — **نه `pg_sleep`.** زمان‌بندی تصادفی آزمون را بی‌ثبات می‌کند.
- اجرای هر CT: **۲۰ بار** زیر `READ COMMITTED` و **۲۰ بار** زیر `SERIALIZABLE`.
- **معیار:** ناوردای پایانی **در هر ۴۰ اجرا** برقرار باشد. یک شکست = شکست آزمون.
- **ناوردای جهانی پس از هر CT** — پرس‌وجوی بررسی:
  - هیچ آفری بیش از یک نسخه‌ی `PUBLISHED` ندارد
  - `publication_status` هر هدف = نوع آخرین رخداد آن (یا `UNPUBLISHED` بدون رخداد)
  - هیچ رخداد یتیمی نیست — رخدادی که projection با آن نخواند

### ۶٫۲ فهرست آزمون

| # | T1 | T2 | ناوردای پایانی |

## ۸. پایداری در برابر migration بعدی (DR)

**خطر:** هر قید ستون راست بند ۷٫۱ برای Prisma **نامرئی** است. تنها پیش‌نمونه‌ی پروژه — migration `20260910020000` — **آخرین** migration است، پس رفتار Prisma با آن هنوز دیده نشده است.

| # | آزمون | انتظار |
|---|---|---|
| **DR-01** | پس از اعمال همه‌ی SQL دستی: `prisma migrate diff --from-migrations … --to-schema-datamodel …` | **خروجی خالی.** هر `DROP INDEX`، `DROP TRIGGER`، `DROP CONSTRAINT` یا `DROP FUNCTION` در خروجی = **یافته** |
| **DR-02** | افزودن یک فیلد بی‌ربط به یک مدل و `prisma migrate dev --create-only` | SQL تولیدشده **فقط** همان فیلد را دارد |
| **DR-03** | همان روی **پایه‌ی `origin/main`** برای ایندکس موجود `external_workspace_link_active_unique` | این ایندکس هم در خطر نیست — **اولین آزمون عملی پیش‌نمونه‌ی موجود پروژه** |
| **DR-04** | `prisma db pull` روی پایگاه نهایی | ثبت: کدام قیدها در schema معکوس دیده می‌شوند و کدام نه |
| **DR-05** | اگر DR-01 تا DR-03 شکست خوردند: یک **فهرست حفاظت‌شده** (نام همه‌ی ایندکس‌ها، CHECKها، Triggerها و Functionهای دستی) + اسکریپت بررسی که هر migration تازه را برای `DROP` روی آن نام‌ها رد کند | اسکریپت migration آلوده را می‌گیرد — **با یک migration آلوده‌ی عمدی آزموده شود** |

**هر نتیجه‌ای در DR-01 تا DR-03، فهرست حفاظت‌شده در CCR ثبت می‌شود.** فرق فقط این است که بررسی خودکارش **اختیاری** است یا **اجباری**.

## ۹. یافته‌ی ۳ — ناهمخوانی درباره‌ی FK `ExternalWorkspaceLink → Organization`

| سند | می‌گوید |
|---|---|
| **طراحی نهایی §۴٫۱ و §۷** | «CCR اول به جدول‌های موجود دست نمی‌زند و FK از آن‌ها به `Organization` نمی‌سازد» · «تغییر یا FK روی جدول‌های موجود V1» عمداً غایب |
| **گزارش گیت §۸** | «افزودن FK به‌صورت ضمنی» مجاز نیست |
| **سند حل موانع §۳٫۲** | ردیف **«ExternalWorkspaceLink → Organization · `RESTRICT` · `RESTRICT`»** در سیاست هر رابطه |

**این دو با هم نمی‌خوانند.** ردیف سند حل موانع می‌تواند «سیاست **وقتی** FK ساخته شد» معنا شود، یا «این FK در CCR اول ساخته می‌شود».

**چرا مهم است:**
- `external_workspace_links` **جدول موجود و منجمد** است.
- اگر ردیف لینکی با `organization_id` بدون ردیف متناظر در `organizations` وجود داشته باشد، **افزودن FK شکست می‌خورد** (FK-12).
- پس این FK یا ترتیب پر کردن `organizations` از شناسه‌های موجود لازم دارد، یا `NOT VALID` + اعتبارسنجی بعدی.

**در این طرح:** FK-12 **فقط به‌عنوان شاهد** اجرا می‌شود و در DDL مبنای آزمون نیست. **تصمیم مالک:** آیا این FK در CCR اول است؟ پیشنهاد من: **نه** — مطابق طراحی نهایی؛ ردیف سند حل موانع به‌عنوان «سیاست آینده» خوانده شود.
