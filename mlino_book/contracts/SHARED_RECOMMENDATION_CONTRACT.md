# قرارداد C — قرارداد مشترک پیشنهاد و اقدام

**نسخه:** ۰٫۱ (طراحی، پیاده نشده) · **تاریخ:** ۹ سپتامبر ۲۰۲۶
**وضعیت:** آماده‌ی بازبینی — **کد نوشته نشده**
**ADR مرتبط:** [`../adr/ADR-0003`](../adr/ADR-0003-shared-recommendation-contract.md)

## ۱. چرا این قرارداد

دو موتور مستقل امروز «پیشنهاد» تولید می‌کنند:

- `implementation/value-engines/` — فرصت عملیاتی از رویداد کسب‌وکار
- `C:\CONTENT STUDIO\service\app\learning\` — پیشنهاد محتوایی از عملکرد واقعی

هیچ‌کدام حذف نمی‌شود. به‌جایش یک **قرارداد بالادستی** تعریف می‌شود که هر دو بتوانند به آن حرف بزنند. بدون این قرارداد، «موتور اقدام روزانه» (بند ۳ چشم‌انداز) نمی‌تواند فهرست واحدی بسازد.

## ۲. مفاهیم لازم — و اینکه امروز کجا هستند

| مفهوم | معنا | V1 امروز | Content Studio امروز |
|---|---|---|---|
| `business` | کدام کسب‌وکار | organization ✅ | workspace (نیازمند نگاشت) |
| `source` | چه چیزی این را تولید کرد | موتور فرصت ✅ | learning ✅ |
| `evidence` | شواهدی که پشت آن است | ✅ | ✅ `learning_signals` |
| `recommendation` | خودِ پیشنهاد | ✅ | ✅ |
| `target_role` | چه کسی باید انجام دهد | ❌ | ❌ |
| `priority` | اولویت | جزئی | ✅ |
| `expected_impact` | اثر انتظاری | ❌ | جزئی |
| `objective` / `kpi` | به کدام هدف وصل است | ❌ | ❌ |
| `effort` | هزینه‌ی انجام | ❌ | ❌ |
| `status` | چرخه‌ی عمر | ✅ | ✅ |
| `outcome` | چه شد | ❌ | ✅ `recommendation_outcomes` |
| `evaluation` | آیا مؤثر بود | ❌ | ✅ `learning_evaluations` |
| `created_at` | زمان ساخت | ✅ | ✅ |
| `freshness` / `expiry` | تا کِی معتبر است | جزئی | ❌ |
| `owner` | شخص مسئول | ❌ | ❌ |
| `permissions` | چه کسی تغییر می‌دهد | ✅ AC-2 | ❌ |
| `visibility` | چه کسی می‌بیند | ✅ AC-2 | ❌ |

**دو ستون آخر جدول، کل استدلال را می‌سازند:** V1 حاکمیت دسترسی دارد ولی سنجش نتیجه ندارد؛ Content Studio سنجش نتیجه دارد ولی حاکمیت ندارد. قرارداد مشترک هر دو را اجباری می‌کند.

## ۳. شکل قرارداد

```
Recommendation
──────────────────────────────────────────────────────────────
  id                   شناسه‌ی یکتا و پایدار
  business_id          → organization متعارف V1        (لازم)
  source               { system, engine, version }     (لازم)
  created_at                                           (لازم)

  evidence[]           چرا این پیشنهاد وجود دارد       (لازم، حداقل یک)
    ├ kind             'metric' | 'event' | 'feedback' | 'observation'
    ├ summary          جمله‌ی انسانی‌خوان
    ├ reference        اشاره به رکورد واقعی منبع
    └ observed_at

  recommendation       چه کاری باید انجام شود          (لازم)
  target_role          کدام نقش مسئول است               (لازم)
                       owner|manager|reception|marketing|sales
  owner                شخص مشخصِ مسئول، اگر تعیین شده   (اختیاری)
                       → نقش همیشه هست؛ شخص ممکن است بعداً تعیین شود
  objective            به کدام هدف/KPI وصل است         (اختیاری در v0.1)
  expected_impact      { direction, magnitude, confidence }
  effort               'low' | 'medium' | 'high'
  priority             عدد یا رتبه

  freshness
    ├ valid_from
    └ valid_until      null = بدون انقضا

  status               'proposed'|'accepted'|'in_progress'
                       |'done'|'dismissed'|'expired'
  outcome              چه واقعاً اتفاق افتاد           (پس از اقدام)
  evaluation           آیا مؤثر بود                    (پس از سنجش)

  permissions          چه کسی می‌تواند وضعیت را تغییر دهد (لازم)
  visibility           چه کسی می‌تواند آن را ببیند        (لازم)
                       → هر دو همیشه از AC-2 عبور می‌کنند
```

## ۴. سه قاعده‌ی سخت

**۱. هیچ پیشنهادی بدون شواهد.** آرایه‌ی `evidence` حداقل یک عضو دارد و هر عضو به یک رکورد واقعی اشاره می‌کند. این همان اصل «هرگز حدس نزن» است: اگر نمی‌توانیم بگوییم چرا، پیشنهاد نمی‌دهیم.

**۲. هیچ پیشنهادی بدون مسئول.** `target_role` اجباری است. پیشنهادی که مسئول ندارد، اقدام نمی‌شود و فقط نویز است.

`owner` (شخص مشخص) عمداً اختیاری است: نقش همیشه از همان ابتدا معلوم است، ولی تخصیص به یک فرد ممکن است بعداً و توسط مدیر انجام شود. اجباری کردنش یعنی موتور باید نام افراد را بداند — که نه می‌داند و نه باید بداند.

**۳. دیده‌شدن همیشه از AC-2.** هیچ مصرف‌کننده‌ای مستقیم از جدول نمی‌خواند. این تنها راهی است که بند ۸ چشم‌انداز (مرز داخلی/قابل‌انتشار) واقعاً اجرا شود.

## ۵. چه چیزی canonical است و چه چیزی adapter می‌خواهد

| جزء | تصمیم |
|---|---|
| **شِمای قرارداد** | **Canonical** — یک تعریف، در V1 |
| **هویت کسب‌وکار** | **Canonical** — organization در V1 |
| **حاکمیت دیده‌شدن** | **Canonical** — AC-2 در V1 |
| موتور فرصت V1 | **Adapter** — خروجی فعلی به قرارداد نگاشت می‌شود |
| موتور یادگیری Content Studio | **Adapter** — `learning_recommendations` به قرارداد نگاشت می‌شود |
| مدل داخلی هر موتور | **دست‌نخورده** |

**نکته:** هیچ موتوری بازنویسی نمی‌شود. هر کدام یک لایه‌ی نگاشت نازک می‌گیرد.

## ۶. مسیر مهاجرت — چهار گام

**گام ۱ — فقط قرارداد.** تعریف نوع مشترک، بدون مصرف‌کننده. هیچ رفتاری عوض نمی‌شود.

**گام ۲ — Adapter خواندنی برای V1.** خروجی موتورهای فرصت به قرارداد نگاشت می‌شود. موتورها دست‌نخورده. اینجا معلوم می‌شود کدام فیلدهای اجباری در V1 وجود ندارند (`target_role`، `expected_impact`، `effort`) و باید پر شوند.

**گام ۳ — Adapter خواندنی برای Content Studio.** همان کار روی `learning_recommendations`. نیازمند قرارداد A (نگاشت workspace) برای پر کردن `business_id`.

**گام ۴ — نمای واحد.** فهرست یکپارچه از هر دو منبع، از پشت AC-2. اینجا بند ۳ چشم‌انداز برای اولین بار واقعاً کار می‌کند.

**ادغام کد دو موتور در این چهار گام نیست** و فقط با توجیه مستقل انجام می‌شود.

## ۸. آنچه عمداً در نسخه‌ی ۰٫۱ نیست

- **امتیازدهی یا رتبه‌بندی بین‌منبعی.** مقایسه‌ی «فرصت عملیاتی» با «پیشنهاد محتوایی» یک قضاوت محصولی است، نه فنی. تا تعریف نشود، فهرست فقط گروه‌بندی می‌شود.
- **اقدام خودکار.** قرارداد فقط پیشنهاد را توصیف می‌کند. اجرای خودکار تصمیم جداست و باید قابل‌بازگشت باشد (بند ۵ چشم‌انداز).
- **یادگیری بین کسب‌وکارها.** استفاده از نتایج یک کسب‌وکار برای بهبود پیشنهاد کسب‌وکار دیگر، یک تصمیم حاکمیتی و حریم‌خصوصی است. → ثبت در دفتر تصمیم‌های باز.
