# مرز Core و ماژول‌های دامنه‌ی کسب‌وکار — OD-40

**تاریخ:** ۱۱ سپتامبر ۲۰۲۶
**نقش:** بازبین معماری ماژولار MLINO V1 (Claude Opus 5)
**وضعیت:** تصمیم معماری — **D-63** (OD-40) و **D-64** (C-05)
**دامنه:** طراحی و مستندسازی — **صفر خط کد، بدون شِما، بدون migration، بدون API، بدون تغییر قرارداد**

---

## ۰. وضعیت زنده پیش از تصمیم

طبق دستور، مخزن پیش از هر تصمیم بررسی شد: همگام با remote (`8911c96`)، درخت کاری تمیز، `HANDOFF_STATE` برابر تحویل OD-39 من. **هیچ عامل دیگری از D-62 به بعد تغییری نداده بود.** آخرین تصمیم D-62 بود ← این تصمیم‌ها **D-63** و **D-64**‌اند.

**اصل حاکم (مصوب مالک):** Core فقط توانمندی‌های بین‌کسب‌وکاری دارد. منطق کسب‌وکار-خاص هرگز وارد Core نمی‌شود. ماژول می‌تواند به Core وابسته باشد؛ Core هرگز به ماژول مشخصی وابسته نیست.

---

## ۱. آنچه کد واقعاً نشان می‌دهد

پیش از هر تصمیم، کد خوانده شد — نه از حافظه.

### ۱٫۱ خبر خوب: جهت وابستگی در سطح import درست است

- **هیچ فایلی در `foundation/`، `briefing/`، `feed/`، `http/` یا `shared-contracts/` از `value-engines/` import نمی‌کند.**
- جهت برعکس درست است: موتورها فقط از `shared-contracts/types` و دو سرویس `foundation` (کلید موقعیت، جست‌وجوی موقعیت) import می‌کنند.
- **شِمای Prisma از پیش باز است:** `EventLog.domainTag` و `OpportunityCurrentState.intendedAudience` از نوع `String`‌اند، نه enum. enumهای Prisma (`EntityType` · `EventType` · `ProducerKind` · `OpportunityState` · `InteractionType` · `OwnershipType` · `ExternalSystem` …) همه عمومی‌اند.
- **هیچ جدول Appointment، Patient، Treatment یا Practitioner وجود ندارد.** موتورها داده‌ی نوبت را از **درگاه‌های فقط‌خواندنی** با پیاده‌سازی درون‌حافظه‌ای می‌خوانند (`InMemoryCapacityRepository` و مشابه).
- **سازوکار ثبت از پیش هست:** `DomainSignalProducerRegistry` برای هر تولیدکننده `allowedDomainTags` خودش را نگه می‌دارد.

### ۱٫۲ نشت: در سطح واژگان، نه import

**Core ماژول را import نمی‌کند، ولی واژگانش را نام می‌برد.** وابستگی Core به ماژول کلینیک از جنس **داده** است: فهرست‌های بسته‌ای که نام خانواده‌ها و مخاطبان کلینیک را سخت‌کد کرده‌اند.

**یک دقیق‌سازی نسبت به نوشته‌ی خودم در OD-39:** نوشته بودم `ALLOWED_DOMAIN_TAGS` «فهرست بسته‌ی سه موتور کلینیک» است. دقیق‌ترش: از چهار برچسب، سه تا مال کلینیک‌اند و `opportunity.interaction` (زنجیره‌ی تعامل روی فرصت، در `compute-projection.ts`) یک **سازوکار Core** است و در Core می‌ماند.

### ۱٫۳ یک واقعیت که راهبرد مهاجرت را تعیین می‌کند

`event_log` **فقط افزودنی** طراحی شده است: اصلاح با `AMENDMENT` و `RETRACTION` انجام می‌شود، و سرویسش هیچ عمل به‌روزرسانی یا حذف ندارد. `compute-projection` تعامل را با **برچسب خانواده‌ی رخداد بنیان‌گذار** تطبیق می‌دهد.

**پس برچسب‌های موجود هرگز تغییر نام نمی‌دهند.** بازنویسی `opportunity.capacity` به `clinic.opportunity.capacity` یعنی بازنویسی تاریخچه‌ی تغییرناپذیر، و شکستن زنجیره‌ی تعامل فرصت‌های باز. هر مهاجرتی باید این برچسب‌ها را **همان‌طور که هستند** نگه دارد.

## ۲. مرز Core

### ۲٫۱ آزمون عضویت در Core

یک مفهوم **فقط وقتی** در Core است که هر سه شرط را داشته باشد:

1. **بدون واژگان صنف معنا دارد** — برای کلینیک، رستوران، فروشگاه و استودیوی محتوا یکسان
2. **معنایش را Core تعریف می‌کند**، نه یک ماژول
3. **زنجیره‌ی Core به آن نیاز دارد**، یا دست‌کم دو ماژول مستقل به همان معنا به آن نیاز دارند

**«مستقل از کسب‌وکار بودن» کافی نیست.** CRM و حسابداری به صنف خاصی تعلق ندارند، ولی **ماژول‌اند**: زنجیره‌ی Core به آن‌ها نیاز ندارد و معنایشان را خودشان تعریف می‌کنند. «افقی» بودن ≠ Core بودن.

### ۲٫۳ زیرلایه‌ی سازوکار Core — موجود در کد

این‌ها پیاده شده‌اند و **ذاتاً عمومی‌اند**. در Core می‌مانند:

- **پذیرش و ثبت رخداد:** `event-admission` · `event-log` · `OCCURRENCE / AMENDMENT / RETRACTION` · کلید موقعیت
- **ثبت تولیدکننده:** `DomainSignalProducerRegistry` — **خود سازوکار**، نه بذرهای کلینیکی‌اش
- **فرصت:** projection · وضعیت فعلی · **زنجیره‌ی تعامل** (`opportunity.interaction`) · `SEEN / ACKNOWLEDGED / DISMISSED`
- **دسترسی:** AC-2 · `OwnershipType`
- **پیوند یکپارچه‌سازی:** `ExternalWorkspaceLink` (D-62)
- **سطوح عملیاتی:** feed و briefing — **به‌عنوان سازوکار**، بدون برچسب‌های صنفی

**«فرصت» مفهوم Core است؛ «خانواده‌ی فرصت» مال ماژول است.** Core می‌داند یک فرصت چیست، چطور پذیرفته، ساخته، دیده و منقضی می‌شود. نمی‌داند «ظرفیت خالی صندلی دندان‌پزشکی» چیست.

## ۳. مرز ماژول کلینیک

| مفهوم | مالک | آنچه Core از آن می‌بیند | قید |
|---|---|---|---|
| **نوبت (Appointment)** | **ماژول کلینیک** / سامانه‌ی مرجع | فقط دسترس‌پذیری (D-56) و قاعده‌ی «درخواست، نه نوشتن» (D-62) | Core موجودیت عمومی «رزرو» **نمی‌سازد** — بند ۳٫۱ |
| **بیمار (Patient)** | **ماژول کلینیک** | `CoreEntity` از نوع `Individual`، بدون ویژگی بالینی | **OD-01** — داده‌ی سلامت، سخت‌گیرانه‌تر از داده‌ی مشتری عادی |
| **درمان (Treatment)** | دو معنا، دو مالک | خدمت فروختنی ← **توانمندی / آفر در Core** با واژگان دسته‌ی کلینیک | سابقه‌ی درمان انجام‌شده و طرح درمان ← **ماژول**؛ **OD-01** |
| **درمانگر (Practitioner)** | **ماژول کلینیک** | شخص = **عضو** (D-57)؛ «درمانگر» = **الگوی نقش ماژول** (D-55) | تخصص و مجوز حرفه‌ای ← ویژگی ماژول؛ منبع قابل‌رزرو ← سامانه‌ی مرجع |
| **ظرفیت (Capacity)** | موتور ← **ماژول کلینیک** | مفهوم دسترس‌پذیری ← **Core** (D-56) | موتور ظرفیت رستوران، اگر ساخته شود، موتور **ماژول رستوران** است با برچسب خودش |
| **نقش‌های کلینیکی** | **ماژول کلینیک** | هیچ — نقش هرگز اجازه نیست (D-55 · D-60) | `receptionist_coordinator`، منشی، دستیار دندان‌پزشک ← الگوهای نقش ماژول |
| **گردش‌کارهای درمانی** | **ماژول کلینیک** | پیشنهاد، اقدام، مشاهده — از نقاط گسترش Core | **رضایت آگاهانه‌ی درمانی ≠ رضایت داده**: اولی مال ماژول، دومی Core (OD-01) |

**سه موتور فعلی** (`cancellation` · `capacity` · `followup`)، درگاه‌هایشان، گروه A کاتالوگ رخداد (`appointment.scheduled` · `working_hours.defined` · `appointment.cancelled` · `appointment.noshow` · `patient.interaction_recorded`)، سه برچسب خانواده‌شان، بذرهای ثبتشان و برچسب‌های فارسی‌شان **از نظر منطقی ماژول کلینیک‌اند.**

### ۳٫۱ چرا Core موجودیت عمومی «رزرو» نمی‌سازد

وسوسه این است: کلینیک نوبت دارد، رستوران رزرو میز، سالن نوبت ← پس «رزرو» را در Core بگذاریم. **نه:**

- معنای رزرو صنفی است: مدت، منبع، لغو، بیعانه، ظرفیت گروهی. هر تعمیمی یا ناقص می‌ماند یا به یک صنف کج می‌شود.
- **Core آنچه لازم است را از قبل دارد:** مفهوم دسترس‌پذیری (D-56)، قاعده‌ی «فقط رزرو وعده است» (D-56)، و قاعده‌ی «سفارش یا رزرو V2 درخواست است که سامانه‌ی مرجع می‌پذیرد» (D-62).

**اگر دو ماژول به یک مفهوم افقی مشترک نیاز داشتند** (مثلاً زمان‌بندی)، آن مفهوم یک **ماژول مشترک** می‌شود، نه Core. ارتقا به Core فقط با گذر از آزمون بند ۲٫۱. **وابستگی ماژول به ماژول** باید اعلام‌شده و بدون چرخه باشد. Core به هیچ‌کدام وابسته نمی‌شود.

## ۴. گسترش‌پذیری ماژول‌ها

| ماژول | در سطح **مفهوم** | در سطح **کد امروز** | پس از CCR بند ۵ |
|---|---|---|---|
| **کلینیک** | ✅ | ✅ کار می‌کند — برچسب‌هایش از پیش در فهرست بسته‌اند | ✅ بدون تغییر رفتار |
| **رستوران** | ✅ سفارش V2 = درخواست (D-62) | ❌ خانواده‌ی فرصت تازه ⇒ CCR | ✅ |
| **خرده‌فروشی** | ✅ موجودی کالا = دسترس‌پذیری (D-56) | ❌ خانواده‌ی فرصت تازه ⇒ CCR | ✅ |
| **Content Studio** | ✅ فقط داده از پیوند (D-62) | ✅ برای پیشنهاد (`source.kind = INTEGRATION`) · ❌ اگر فرصت بسازد | ✅ |
| **CRM** | ✅ ماژول افقی، نه Core | ❌ مخاطب تازه یا خانواده‌ی تازه ⇒ CCR | ✅ · بخش داده‌ی فردی ← **OD-01** |
| **حسابداری** | ✅ مشاهده و شاهد برای ارزیابی (D-50) | ✅ اگر فقط شاهد بدهد · ❌ اگر فرصت بسازد | ✅ · حسابداری هرگز پول جابه‌جا نمی‌کند |

**جواب:** در سطح **مفهوم**، هر شش ماژول **بدون هیچ تغییری در مفاهیم Core** جا می‌گیرند. همه‌ی نقاط گسترش لازم در D-52 تا D-62 تعریف شده‌اند.

در سطح **کد**، سه نقطه در قرارداد منجمد هر ماژولی را که **فرصت یا مخاطب تازه** بخواهد می‌بندد. رفعش **یک CCR یک‌باره** است. این CCR مفهومی به Core **نمی‌افزاید**؛ فقط **وابستگی Core به واژگان کلینیک را برمی‌دارد**. پس از آن، افزودن ماژول دیگر هیچ تغییری در Core نمی‌خواهد.

## ۵. راهبرد مهاجرت

### ۵٫۱ چهار دسته

| دسته | چه |
|---|---|
| **در Core می‌ماند** | همه‌ی بند ۲٫۲ و ۲٫۳ · برچسب `opportunity.interaction` · سازوکار ثبت تولیدکننده · AC-2 · feed و briefing به‌عنوان سازوکار |
| **مال ماژول می‌شود** | سه موتور کلینیک و درگاه‌هایشان · گروه A کاتالوگ رخداد · سه برچسب خانواده · بذر ثبت موتورها · برچسب‌های فارسی خانواده‌ها · واژه‌ی مخاطب `receptionist_coordinator` · همه‌ی مفاهیم بند ۳ |
| **بعداً منسوخ می‌شود** | ثابت `ALLOWED_DOMAIN_TAGS` به‌عنوان **فهرست بسته** · `ActorContext.role` به‌عنوان مبنای دسترسی · `IntendedAudience` به‌عنوان **union بسته** · نام و جای `seedV1CoreProducerRegistry` · `FAMILY_LABELS` درون briefing · اعتبارسنجی `read-api` با ثابت |
| **موقتاً می‌ماند — واقعیت پیاده‌سازی** | همه‌ی موارد بالا **تا CCR** · مکان فیزیکی موتورها در `implementation/value-engines/` · بررسی «نقش شناخته‌شده» در AC-2 (به هر دو نقش دسترسی یکسان می‌دهد — D-55) تا مجوزدهی مبتنی بر اعطا (D-57) پیاده شود · **سه برچسب موجود کلینیک — برای همیشه، بدون تغییر نام** (بند ۱٫۳) |

### ۵٫۲ سه مرحله

**م۰ — طبقه‌بندی منطقی (همین سند، بدون کد):** موارد «مال ماژول» از امروز **ماژول کلینیک** شمرده می‌شوند. هیچ کدی جابه‌جا نمی‌شود.

**م۱ — یک CCR روی قرارداد منجمد (با مجوز جداگانه‌ی مالک، وقتی زمان‌بندی شد):**
- `DomainTag`: از فهرست بسته ← **واژگان ثبت‌شده**. اعتبار یک برچسب = ثبت‌بودنش برای آن تولیدکننده در registry. (نیمه‌ی دوم این بررسی از قبل وجود دارد.)
- برچسب‌های **تازه** فضانام‌دار: `<ماژول>.<خانواده>` — مثلاً `restaurant.opportunity.table_capacity`
- **چهار برچسب موجود بدون فضانام حفظ می‌شوند:** سه تا به‌عنوان برچسب **ثبت‌شده‌ی ماژول کلینیک**، `opportunity.interaction` به‌عنوان برچسب **Core**. هیچ ردیفی بازنویسی نمی‌شود.
- **Core اعتبارسنجی می‌کند، معنا را تفسیر نمی‌کند** — همان الگوی عمل‌های فضانام‌دار D-62
- `IntendedAudience`: از union بسته ← **واژگان مسیریابی ثبت‌شده‌ی ماژول**، همان «مسئولیت» D-55
- `ActorContext.role`: منسوخ به‌عنوان مبنای دسترسی. **جایگزینش در این CCR تعیین نمی‌شود** — به پیاده‌سازی D-57 گره خورده است
- **بدون migration دیتابیس:** ستون‌ها از قبل `String`‌اند

**م۲ — ساختار کد (بعدتر، با دستور جداگانه):** انتقال فیزیکی موتورها به بسته‌ی ماژول کلینیک؛ ثبت موتورها و برچسب‌های نمایشی از سوی خود ماژول؛ اعتبارسنجی `read-api` با registry.

### ۵٫۳ آنچه هرگز انجام نمی‌شود

- **تغییر نام برچسب‌های ذخیره‌شده در `event_log`**
- **import ماژول از درون Core** — امروز رعایت می‌شود و باید بماند
- **شاخه‌ی صنفی درون Core** (`if tag === 'clinic…'`). شاخه روی `opportunity.interaction` مجاز است چون سازوکار Core است
- **افزودن واژه‌ی صنفی تازه به فایل‌های Core تا پیش از CCR** — محافظ برای پیاده‌سازان، بدون کد

---

## ۶. C-05 — حل‌شده با جداسازی صریح مالک (D-64)

دستور OD-40 جداسازی را صریح داد:

- **Core:** هوش و ارکستراسیون مستقل از کسب‌وکار
- **V1:** حقیقت کسب‌وکار و سیستم‌عامل
- **V2:** کشف، تطبیق، تعامل و تجربه

| پرسش | پاسخ |
|---|---|
| **ارکستراسیون تجربه** | **Core** |
| **مالکیت دستیار** (زیربنا: استدلال، استفاده از قراردادها، قواعد ایمنی) | **Core** |
| **رابط دستیار** | **V2** |
| **تجربه‌ی تطبیق** | **V2** — همان D-52 بند ۸: ربط کار V2 است |
| **کشف · رندر تجربه** | **V2** |

### ۶٫۱ یک اصلاح در خوانش خودم

در OD-39 نوشته بودم ارکستراسیون تجربه «Core است **و در سمت V2**». **جداسازی مالک دقیق‌تر است و آن را اصلاح می‌کند:** ارکستراسیون تجربه **مال Core است، نه منطق V2.** V2 فقط **رندر** می‌کند. جای‌گذاری بافت OD-26 («ارکستراسیون تجربه = V2») با این تصمیم **جایگزین** شد.

**Core و V1 دو محور جدا نیستند که تناقض بسازند:** V1 یک سیستم‌عامل ماژولار است = **Core + ماژول‌ها**. Core **تعریف** مفاهیم را دارد و V1 **نمونه‌های** آن‌ها را به‌عنوان حقیقت نگه می‌دارد. پس «توانمندی در Core» و «توانمندی مال V1» (D-52) با هم سازگارند.

### ۶٫۲ یک محافظ — پیامد مستقیم D-52

**خروجی ارکستراسیون تجربه برای کاربر نهایی خودش یک خروجی V1 ← V2 است.** پس فقط از **تصویر منتشرشده** (D-52) و از مسیر AC-2 ساخته می‌شود. در غیر این صورت Core از در پشتی حقیقت داخلی را به V2 نشت می‌دهد.

- ارکستراسیون **تصمیم می‌گیرد** گام بعدی تجربه چیست و آن را **مستقل از رندر** توصیف می‌کند. V2 آن را **نشان می‌دهد**.
- ارکستراسیون **حقیقت نمی‌نویسد.** سفارش و رزرو درخواست‌اند (D-62).
- جریان‌های صنفی (مثلاً درخواست نوبت کلینیک) را **ماژول ثبت می‌کند**. موتور ارکستراسیون عمومی است.
- دستیار: هوش مصنوعی بیرون از مسیر تصمیم حاکمیتی (D-58)؛ **هیچ تفویض دائمی** (D-57)؛ «هرگز حدس نزن» در هر دو جهت (D-50 · D-52).

### ۶٫۳ یک ابهام باقی‌مانده → C-06 (باز، **غیرمسدودکننده**)

«رابط دستیار = V2» برای **کاربر نهایی** روشن است. برای **دستیار اعضای خود کسب‌وکار** — که روی حقیقت داخلی منتشرنشده کار می‌کند — روشن نیست. D-52 می‌گوید V2 فقط تصویر منتشرشده را دریافت می‌کند. اگر V2 رابط دستیار عضو را هم رندر کند، داده‌ی منتشرنشده به V2 می‌رسد.

**خوانش من:** «رابط دستیار = V2» یعنی دستیار کاربر نهایی. سطوح عملیاتی اعضا (feed، briefing و دستیار داخلی) پشت AC-2 می‌مانند. اگر مالک بخواهد V2 سطح احراز‌هویت‌شده‌ی اعضا هم باشد، **پالایش صریح D-52** لازم است. **D-63 و D-64 به این مورد وابسته نیستند.**

## ۷. تصمیم — D-63 (OD-40)

**۱.** Core فقط مفاهیمی را دارد که از **آزمون سه‌شرطی** بند ۲٫۱ بگذرند. «مستقل از صنف» کافی نیست — CRM و حسابداری ماژول‌اند.

**۲.** **Core هیچ واژه‌ی صنفی را نام نمی‌برد** — نه در import، نه در فهرست بسته، نه در بذر، نه در برچسب نمایشی. وابستگی از جنس داده هم وابستگی است.

**۳.** «فرصت» مفهوم Core است؛ **«خانواده‌ی فرصت» مال ماژول است** و ثبت می‌شود. `opportunity.interaction` سازوکار Core است.

**۴.** Core **هیچ نام نقشی** ندارد. واژگان نقش و مخاطب را ماژول تامین می‌کند؛ نقش هرگز اجازه نیست (D-55 · D-60).

**۵.** نوبت، بیمار، سابقه‌ی درمان، درمانگر (به‌عنوان ویژگی و منبع)، موتور ظرفیت، نقش‌های کلینیکی و گردش‌کارهای درمانی **مال ماژول کلینیک‌اند.** خدمت فروختنی ← توانمندی و آفر Core. درمانگر به‌عنوان شخص ← عضو Core.

**۶.** Core موجودیت عمومی «رزرو» نمی‌سازد. مفهوم افقی مشترک ← **ماژول مشترک**، نه Core. وابستگی ماژول به ماژول اعلام‌شده و بدون چرخه.

**۷.** سه موتور کلینیک و همه‌ی واژگانشان **از امروز منطقاً ماژول کلینیک‌اند (م۰).** کدی جابه‌جا نمی‌شود.

**۸.** رفع نشت = **یک CCR یک‌باره روی قرارداد منجمد (م۱)**، با مجوز جداگانه‌ی مالک: فهرست بسته ← واژگان ثبت‌شده؛ برچسب تازه فضانام‌دار؛ **Core اعتبارسنجی می‌کند، تفسیر نمی‌کند.**

**۹.** **برچسب‌های موجود هرگز تغییر نام نمی‌دهند.** `event_log` فقط افزودنی است و زنجیره‌ی تعامل به برچسب بنیان‌گذار وابسته است.

**۱۰.** تا CCR، **هیچ واژه‌ی صنفی تازه‌ای به فایل‌های Core افزوده نمی‌شود.**

**۱۱.** پس از CCR، افزودن ماژول **هیچ تغییری در Core** نمی‌خواهد.

## ۸. تصمیم — D-64 (C-05)

**۱.** ارکستراسیون تجربه = **Core**. زیربنای دستیار = **Core**. رابط دستیار، تطبیق، کشف و رندر تجربه = **V2**. جای‌گذاری بافت OD-26 **جایگزین** شد.

**۲.** V1 = Core + ماژول‌ها. Core تعریف می‌کند؛ V1 حقیقت را نگه می‌دارد؛ V2 تجربه را می‌سازد.

**۳.** **خروجی ارکستراسیون برای کاربر نهایی فقط از تصویر منتشرشده (D-52) و از مسیر AC-2.** ارکستراسیون حقیقت نمی‌نویسد.

**۴.** جریان‌ها و مهارت‌های صنفی دستیار را **ماژول ثبت می‌کند.** موتور عمومی Core است.

## ۱۱. حکم نهایی: **A — آماده**

**تصمیم OD-40 کامل است** و C-05 با جداسازی صریح مالک بسته شد. هیچ مانع مشخصی برای خود این تصمیم باقی نمانده است.

**برای روشن بودن — این‌ها مانع نیستند، گام‌های برنامه‌ریزی‌شده یا موارد شناخته‌شده‌اند:**
- **اجرای م۱** یک CCR روی قرارداد منجمد است و **مجوز جداگانه‌ی مالک** را وقتی زمان‌بندی شد لازم دارد. این دستور صراحتاً تغییر قرارداد را منع کرده بود، پس انجام نشد.
- **بخش داده‌ی فردی** ماژول کلینیک (بیمار، سابقه‌ی درمان) و CRM ← **OD-01**. مورد شناخته‌شده است، تازه نیست.
- **C-06** — ابهام دستیار اعضا — باز و غیرمسدودکننده است.

**پیشنهاد:** یک ADR برای اصل «Core هیچ واژه‌ی صنفی را نام نمی‌برد» (D-63) و جداسازی سه‌لایه (D-64). در این دستور نوشته نشد چون دامنه‌ی به‌روزرسانی محدود بود.
