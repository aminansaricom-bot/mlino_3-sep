# قرارداد A — نگاشت `workspace` ⇄ `organization`

**نسخه:** ۰٫۱ (طراحی، پیاده نشده) · **تاریخ:** ۹ سپتامبر ۲۰۲۶
**وضعیت:** آماده‌ی بازبینی — **کد نوشته نشده**

---

## ۱. مسئله

«یک کسب‌وکار» امروز دو نمایندگی مستقل دارد و هیچ پیوندی بینشان نیست:

| | V1 | Content Studio |
|---|---|---|
| موجودیت | `CoreEntity` + `organization` | `workspace` |
| دیتابیس | Postgres V1 (Prisma) | Postgres Content Studio (SQL خام) |
| حاکمیت | AC-2 | ندارد |

بدون نگاشت، هیچ پیشنهاد محتوایی نمی‌تواند به کسب‌وکار واقعی نسبت داده شود، و AC-2 نمی‌تواند درباره‌اش تصمیم بگیرد.

## ۲. اصل حاکم

**V1 منبع حقیقت متعارف هویت کسب‌وکار است.**

`workspace` یک **نمایندگی محلی** در ماژول محتواست، نه یک هویت مستقل. هر `workspace` باید به‌طور **قطعی و قابل‌ممیزی** به یک `organization` در V1 نگاشت شود.

### سه قید

**قطعی بودن.** یک `workspace_id` همیشه به همان `organization_id` می‌رسد. بدون حدس، بدون تطبیق فازی.

**ممنوعیت نگاشت بر اساس نام.** «کلینیک آرتا» در دو سیستم ممکن است دو کسب‌وکار متفاوت باشد، یا یک کسب‌وکار با دو املا. تطبیق نام یک منبع خطای خاموش است.

**قابل‌ممیزی بودن.** باید بشود پرسید «این نگاشت کِی، توسط چه کسی، و بر چه اساسی ثبت شد؟» و جواب گرفت.

## ۳. مدل داده‌ی پیشنهادی

نگاشت **در V1 زندگی می‌کند**، چون V1 منبع حقیقت است.

```
ExternalWorkspaceLink
─────────────────────────────────────────────────────────────
  id                    شناسه‌ی یکتا
  organization_id       → هویت متعارف V1                (لازم)
  system                'content_studio' | ...           (لازم)
  external_workspace_id شناسه در سیستم بیرونی            (لازم)
  status                'active' | 'suspended' | 'revoked'
  linked_at             زمان ثبت پیوند
  linked_by_actor_id    چه کسی ثبت کرد                   (لازم)
  link_basis            'owner_confirmed' | 'admin_manual'
  revoked_at            زمان لغو، اگر لغو شده
  revoked_by_actor_id   چه کسی لغو کرد
  note                  متن آزاد برای ممیزی
```

**قیود یکتایی:**

- `UNIQUE (system, external_workspace_id) WHERE status = 'active'` — یک workspace در هر لحظه حداکثر به یک organization فعال وصل است.
- یک `organization` **می‌تواند** چند workspace داشته باشد (مثلاً چند شعبه یا چند کانال) — این عمداً مجاز است.

## ۴. چرا سمت Content Studio چیزی اضافه نمی‌شود

وسوسه‌ی طبیعی این است که یک ستون `organization_id` به جدول `workspace` اضافه شود. **این کار انجام نمی‌شود**، به سه دلیل:

۱. دو نسخه‌ی نگاشت یعنی احتمال ناهماهنگی — و آن‌وقت کدام درست است؟
۲. Content Studio نباید به شِمای V1 وابسته شود؛ استقلالش همان چیزی است که تصمیم ۳ حفظش کرده.
۳. لغو پیوند باید **یک** جا اتفاق بیفتد تا AC-2 بتواند بلافاصله به آن اتکا کند.

Content Studio هیچ تغییری در مدل داده‌اش نمی‌گیرد. فقط `workspace_id` خودش را در تماس‌های بیرونی اعلام می‌کند.

## ۵. جهت جریان داده

```
Content Studio  ──(workspace_id)──►  V1 Resolver  ──►  organization_id  ──►  AC-2
```

- **Content Studio هرگز `organization_id` را ذخیره نمی‌کند.** آن را در پاسخ می‌گیرد و استفاده می‌کند.
- **V1 هرگز `workspace_id` را به‌عنوان هویت نمی‌پذیرد.** فقط آن را به هویت متعارف ترجمه می‌کند.
- اگر پیوند فعالی نباشد، پاسخ **صریحاً «پیوند ندارد»** است — نه صفر، نه پیش‌فرض، نه حدس. **Fail-closed.**

## ۶. رابط عملیاتی (طرح، نه پیاده‌سازی)

```
resolveWorkspace(system, external_workspace_id)
  → { status: 'linked', organization_id }
  → { status: 'not_linked' }
  → { status: 'revoked', revoked_at }
```

**قید امنیتی:** این رابط نباید به «existence oracle» تبدیل شود. یعنی نباید بشود با آن فهمید کدام workspace‌ها در V1 وجود دارند. همان درسی که در مرز HTTP نسخه‌ی ۱ گرفته شد — `not_linked` و «وجود ندارد» باید از بیرون یکسان به‌نظر برسند.

## ۷. تعارض‌ها و پیامدها

**فایل منجمد.** افزودن `ExternalWorkspaceLink` یعنی تغییر `prisma/schema.prisma` که **منجمد** است. **این کار به یک CCR مصوب نیاز دارد.** بدون آن، پیاده‌سازی شروع نمی‌شود.

**داده‌ی موجود.** Content Studio همین حالا رکورد `workspace` دارد. هیچ‌کدام پیوند ندارند. مهاجرت یعنی ثبت دستی و تاییدشده‌ی پیوندها — **نه حدس خودکار از روی نام**.

**رضایت.** پیوند دادن یک workspace به یک organization یعنی داده‌ی محتوایی به هویت کسب‌وکار وصل می‌شود. تا وقتی سیاست R8-a تعریف نشده، این نگاشت **فقط برای داده‌ی خودِ کسب‌وکار** معتبر است، نه داده‌ی مشتریانش.

## ۸. معیار پذیرش (برای وقتی که پیاده شود)

۱. یک `workspace` بدون پیوند فعال، هرگز `organization_id` نمی‌گیرد.
۲. پیوند لغوشده مثل پیوند نبوده رفتار می‌کند.
۳. تلاش برای پیوند دوم روی یک workspace فعال، رد می‌شود.
۴. هر پیوند و هر لغو، بازیگر و زمانش ثبت می‌شود.
۵. هیچ نگاشتی از روی نام انجام نمی‌شود — با تست اثبات شود.
۶. رابط، وجود یا نبود سازمان را افشا نمی‌کند.
