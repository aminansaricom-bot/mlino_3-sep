# سؤالات بازبینی مرکزی

**این سند فقط سؤالات را ثبت می‌کند. پاسخ قطعی داده نشده مگر جایی که شواهد سخت موجود، مستقیماً و صراحتاً آن را اثبات کند — و حتی در آن موارد، تصمیم نهایی به‌عهده‌ی بازبین مستقل است.**

۱. آیا FP-01 اصل Producer≠Owner را به‌درستی اعمال می‌کند؟
   *شواهد مرتبط:* [[FP01_REVIEW_MAP.md]] — هیچ تولیدکننده مستقیماً به `event_log` نمی‌نویسد؛ فقط از طریق `EventAdmissionService`.

۲. آیا IC-13 واقعاً تنها مسیر نوشتن Event Log است؟
   *شواهد مرتبط:* grep تأیید‌شده در [[FP01_REVIEW_MAP.md]] — تنها یک `prisma.eventLog.create()` تولیدی. **این سؤال با شواهد کد قوی پشتیبانی می‌شود، اما نتیجه‌گیری قطعی به بازبین مستقل واگذار می‌شود.**

۳. آیا Idempotency تحت درخواست‌های هم‌زمان (Concurrent) ایمن است؟
   *یادداشت:* تست موجود (`event-admission.spec.ts`) درخواست‌های **متوالی** تکراری را می‌آزماید، نه هم‌زمان واقعی (Race روی `unique_key` با دو Insert هم‌زمان). این یک **شکاف تست شناخته‌شده** است — بدون تست Concurrency واقعی در Wave 1.

۴. آیا جداسازی Tenant/سازمان به‌صورت ساختاری (نه فقط قراردادی) اعمال شده؟
   *شواهد:* هر جدول فعال دارای `organization_id` است؛ هر Query بررسی‌شده این فیلد را در `where` دارد ([[DATABASE_REVIEW_MAP.md]]). بدون Row-Level Security در سطح Postgres — جداسازی صرفاً در سطح کد اپلیکیشن است.

۵. آیا FP-03 به‌درستی AC-2 را بدون بازتعریف آن پیاده می‌کند؟
   *شواهد:* [[FP03_REVIEW_MAP.md]] — کامنت صریح کد «AC-2 ≠ این فایل».

۶. آیا F-01/F-02/F-03 به‌عنوان Value Engine های محدود و خالص باقی مانده‌اند؟
   *شواهد:* بدون Import بین‌Featureای؛ بدون دسترسی مستقیم Prisma ([[FEATURE_REVIEW_MAP.md]]، [[WAVE_1_VALIDATION_RESULTS.md]]).

۷. آیا F-03 صرفاً آگاهی‌بخش باقی مانده، بدون هیچ توان اجرایی؟
   *شواهد:* ممنوعیت صریح Import پیام‌رسانی، تست‌شده به‌طور خودکار ([[FEATURE_REVIEW_MAP.md]]).

۸. آیا F-04 جداسازی نقش و وضعیت actor را حفظ می‌کند؟
   *شواهد:* چهار تست SECURITY در [[FEATURE_REVIEW_MAP.md]] بخش F-04.

۹. آیا F-04 به‌طور ناخواسته منطق تشخیص Opportunity در خود دارد؟
   *شواهد:* تست معماری صریح موجود؛ بازبین باید مستقل تأیید کند منطق واقعاً غایب است، نه فقط تست موجود کافی است.

۱۰. آیا F-05 حتی بدون دسترسی به هوش مصنوعی مفید باقی می‌ماند؟
    *شواهد:* Fallback الزامی تست‌شده ([[FEATURE_REVIEW_MAP.md]] بخش F-05).

۱۱. آیا قراردادهای مشترک بدون انحراف پیاده‌سازی شده‌اند؟
    *شواهد:* [[SHARED_CONTRACT_IMPLEMENTATION_MAP.md]] — صفر DEVIATION یافت‌شده؛ سه مورد NOT IMPLEMENTED (به دلیل نبود لایه‌ی HTTP و FP-02، نه انحراف).

۱۲. آیا Prisma Schema فعلی با طراحی DB فاز ۴A مطابقت دارد؟
    *یادداشت:* این سند به‌طور مستقیم Diff خط‌به‌خط بین Schema فعلی و `V1_DATABASE_DESIGN.md` انجام نداد (خارج از دامنه‌ی این بسته‌بندی صرفاً-شواهد) — نگاشت ساختاری در [[DATABASE_REVIEW_MAP.md]] موجود است؛ تطابق دقیق باید توسط بازبین با مقایسه‌ی مستقیم دو سند تأیید شود.

۱۳. آیا actor→CoreEntity واقعاً یک الزام معماری منجمد است؟
    *پاسخ صریح ثبت‌شده در [[ACTOR_COREENTITY_FINDING.md]]: **UNKNOWN/رد** — هیچ سند منجمدی این را صراحتاً الزام نکرده.*

۱۴. اگر پاسخ ۱۳ منفی است، این نیازمندی از کجا آمده؟
    *پاسخ ثبت‌شده در [[ACTOR_COREENTITY_FINDING.md]] بند H: ترکیب دو انتخاب پیاده‌سازی (F-04 خط ۴۷ + FP-01 خط ۳۸–۴۹)، آشکارشده توسط طراحی Fixture تست.*

۱۵. آیا Wave 1 برای پیشروی به FP-02 ایمن است؟
    *این سؤال عمداً بدون پاسخ باقی می‌ماند — این دقیقاً همان تصمیمی است که این بازبینی مرکزی باید بگیرد، نه این بسته‌بندی.*
