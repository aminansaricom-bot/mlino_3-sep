# CONTRACT_CHANGE_REQUEST — `ExternalWorkspaceLink`: نگاشت هویت کسب‌وکار بین V1 و سیستم‌های بیرونی

**وضعیت: DRAFT — پیشنهاد، تصویب‌نشده، اعمال‌نشده.**

هیچ تغییری در `prisma/schema.prisma` یا `shared-contracts/types.ts` در پاس تولید این سند انجام نشده. هیچ migration ساخته نشده. هیچ کد دیتابیسی نوشته نشده. تا تایید صریح مالک محصول + بازبینی مستقل نباید انجام شود.

**صادر شده طبق:** تصمیم مالک محصول — «CONTENT STUDIO REMOTE DECISION + NEXT IMPLEMENTATION STEP» بند ۳
**مبنای معماری:** `mlino_book/adr/ADR-0004-workspace-organization-mapping.md` · `mlino_book/contracts/WORKSPACE_ORGANIZATION_MAPPING.md`
**مبنای سیاستی:** `V1_MINIMUM_AC2_ACCESS_POLICY.md` v1.1

## ۱. مسئله

«یک کسب‌وکار» امروز دو نمایندگی مستقل دارد و **هیچ پیوندی بینشان نیست**:

| سیستم | موجودیت | دیتابیس |
|---|---|---|
| MLINO V1 | `CoreEntity` + `organizationId` | Postgres V1 (Prisma) |
| Content Studio | `workspace` (جدول ۱ از ۲۶) | Postgres مستقل (SQL خام) |

بازخوانی مستقیم، نه فرض: در `prisma/schema.prisma` هیچ مدل، فیلد یا رابطه‌ای وجود ندارد که به یک سیستم بیرونی اشاره کند. `organizationId` در همه‌جا یک `String` ساده است بدون هیچ نگاشت خارجی.

**پیامد عملی:** هیچ پیشنهاد محتوایی تولیدشده در Content Studio نمی‌تواند به یک کسب‌وکار واقعی در V1 نسبت داده شود، و AC-2 نمی‌تواند درباره‌اش تصمیم بگیرد. قرارداد مشترک پیشنهاد (v1.0، پیاده‌شده) فیلد `business_id` را **اجباری** کرده و مقدارش را از `organization` متعارف V1 می‌خواهد — بدون این نگاشت، Adapter سمت Content Studio اصلاً نمی‌تواند ساخته شود.

## ۲. انگیزه

**چرا حالا و نه بعداً:** گام ۲ نقشه‌ی راه مصوب دقیقاً همین است، و گام‌های ۳ تا ۵ (دیتابیس، API، رابط کاربری) همگی به آن وابسته‌اند.

**چرا این یک تصمیم حاکمیتی است، نه فقط فنی:** این نقطه‌ای است که دو سیستم برای اولین بار **هویت مشترک** پیدا می‌کنند. از این لحظه، یک تصمیم اشتباه در نگاشت یعنی داده‌ی یک کسب‌وکار به کسب‌وکار دیگری نسبت داده شود — که مستقیماً مرز AC-2 را می‌شکند.

**چرا نمی‌شود بدون تغییر قرارداد انجامش داد:** هر راه دیگری یا نگاشت را ضمنی می‌کند (بر اساس نام، که ممنوع است) یا آن را بیرون از V1 نگه می‌دارد (که اصل «V1 منبع حقیقت متعارف» را نقض می‌کند).

## ۳. بدیل‌های بررسی‌شده

### ۳.۱. ستون `organization_id` روی جدول `workspace` در Content Studio — **رد شد**

ساده‌ترین راه به‌نظر می‌آید. رد شد به چهار دلیل:

- **دو نسخه‌ی نگاشت** یعنی احتمال ناهماهنگی، و آن‌وقت کدام درست است؟
- **لغو باید یک جا اتفاق بیفتد.** اگر پیوند در دو جا ثبت شود، پنجره‌ای باز می‌ماند که AC-2 در آن به داده‌ی کهنه اتکا می‌کند.
- Content Studio به شِمای V1 وابسته می‌شود — دقیقاً همان چیزی که ADR-0002 از آن پرهیز کرد.
- **مالک محصول این را صریحاً ممنوع کرد.**

### ۳.۲. نگاشت بر اساس نام کسب‌وکار — **رد شد**

«کلینیک آرتا» در دو سیستم ممکن است دو کسب‌وکار متفاوت باشد، یا یک کسب‌وکار با دو املا. تطبیق نام یک **منبع خطای خاموش** است: هیچ‌وقت خطا نمی‌دهد، فقط گاهی داده را به کسب‌وکار اشتباه می‌چسباند.

### ۳.۳. فایل پیکربندی یا متغیر محیطی — **رد شد**

قابل‌ممیزی نیست («کِی و توسط چه کسی ثبت شد؟» جواب ندارد)، نسخه‌دار نیست، و در چند نمونه‌ی اجرایی واگرا می‌شود.

### ۳.۴. سرویس هویت جداگانه — **رد شد برای V1**

از نظر معماری تمیزتر است، ولی یک سرویس سوم اضافه می‌کند در حالی که کل مسئله یک جدول نگاشت است. برای مقیاس امروز، پیچیدگی بی‌مورد.

### ۳.۵. جدول نگاشت در V1 — **پیشنهاد این CCR**

یک منبع حقیقت، یک نقطه‌ی لغو، Content Studio دست‌نخورده، و کاملاً قابل‌ممیزی.

## ۴. مدل داده‌ی پیشنهادی

⚠️ **این فقط پیشنهاد است. اعمال نشده.**

```prisma
enum ExternalSystem {
  CONTENT_STUDIO
  // مقادیر بعدی فقط با CCR جداگانه اضافه می‌شوند
}

enum ExternalLinkStatus {
  ACTIVE
  SUSPENDED
  REVOKED
}

enum ExternalLinkBasis {
  OWNER_CONFIRMED      // مالک کسب‌وکار خودش تایید کرده
  ADMIN_MANUAL         // ثبت دستی توسط اپراتور MLINO
}

model ExternalWorkspaceLink {
  id                   String              @id @default(uuid())
  organizationId       String              @map("organization_id")
  system               ExternalSystem
  externalWorkspaceId  String              @map("external_workspace_id")

  status               ExternalLinkStatus  @default(ACTIVE)
  basis                ExternalLinkBasis

  linkedAt             DateTime            @map("linked_at")
  linkedByActorId      String              @map("linked_by_actor_id")
  revokedAt            DateTime?           @map("revoked_at")
  revokedByActorId     String?             @map("revoked_by_actor_id")
  note                 String?

  @@index([organizationId])
  @@map("external_workspace_links")
}
```

**قید یکتایی — مهم‌ترین بخش این مدل:**

```sql
CREATE UNIQUE INDEX external_workspace_link_active_unique
  ON external_workspace_links (system, external_workspace_id)
  WHERE status = 'ACTIVE';
```

یک ایندکس یکتای **جزئی**. یعنی یک workspace در هر لحظه حداکثر به **یک** organization فعال وصل است، ولی تاریخچه‌ی پیوندهای لغوشده حفظ می‌شود.

Prisma این را به‌صورت بومی پشتیبانی نمی‌کند و نیاز به SQL خام در migration دارد — این را به‌عنوان یک ریسک واقعی در بند ۱۱ ثبت کرده‌ام.

**چرا `String` و نه رابطه‌ی Prisma به `CoreEntity`:** در شِمای فعلی `organizationId` همه‌جا `String` ساده است بدون رابطه. پیروی از همان الگو یعنی صفر تغییر در مدل‌های موجود.

## ۵. مالکیت

| چیز | مالک |
|---|---|
| جدول نگاشت | **V1** — منبع حقیقت متعارف |
| `organizationId` | **V1** |
| `externalWorkspaceId` | Content Studio (V1 فقط ارجاعش می‌دهد، اعتبارسنجی‌اش نمی‌کند) |
| تصمیم پیوند/لغو | **V1**، با بازیگر ثبت‌شده |

**Content Studio هیچ ستونی نمی‌گیرد و هیچ تغییری در دیتابیسش انجام نمی‌شود.** فقط `workspace_id` خودش را در تماس بیرونی اعلام می‌کند و `organization_id` را در پاسخ می‌گیرد — **و ذخیره‌اش نمی‌کند.**

## ۶. کاردینالیتی

```
organization  ←──── 1 : N ────→  ExternalWorkspaceLink
                                          │
                                     N : 1 (فعال)
                                          ↓
                                 external workspace
```

**یک organization می‌تواند چند workspace داشته باشد** — عمداً مجاز. یک کسب‌وکار ممکن است چند شعبه یا چند کانال محتوایی داشته باشد.

**یک workspace در هر لحظه حداکثر یک organization فعال دارد** — با ایندکس یکتای جزئی اجبار می‌شود، نه با قرارداد شفاهی.

**تاریخچه‌ی چند پیوند لغوشده روی یک workspace مجاز است** — لازم است تا بشود گفت «این workspace قبلاً به کسب‌وکار دیگری وصل بود».

## ۷. چرخه‌ی عمر

```
                  ┌──────────┐
   ثبت پیوند ───→ │  ACTIVE  │
                  └────┬─────┘
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
    ┌───────────┐            ┌───────────┐
    │ SUSPENDED │ ←────────→ │  REVOKED  │
    └───────────┘            └───────────┘
      موقت، برگشت‌پذیر         نهایی، بی‌بازگشت
```

- `ACTIVE → SUSPENDED` — تعلیق موقت (مثلاً اختلاف در تایید مالکیت). قابل بازگشت.
- `ACTIVE → REVOKED` یا `SUSPENDED → REVOKED` — لغو نهایی. **بازگشت ندارد**؛ برای وصل دوباره باید یک رکورد پیوند **جدید** ساخته شود.
- `REVOKED → *` — ممنوع.

**فقط `ACTIVE` معتبر است.** `SUSPENDED` و `REVOKED` هر دو مثل «پیوند ندارد» رفتار می‌کنند — **fail-closed**، بدون استثنا.

## ۸. مجوزها

**چه کسی می‌تواند پیوند بسازد یا لغو کند:** فقط بازیگری با نقش مدیریتی در همان organization، یا اپراتور MLINO با `ADMIN_MANUAL`. هر دو حالت `linkedByActorId` را اجباری پر می‌کنند.

**چه کسی می‌تواند نگاشت را بخواند:** از AC-2 عبور می‌کند مثل هر داده‌ی دیگر.

⚠️ **قید امنیتی — تکرار درسی که قبلاً گرفته شد:**

رابط `resolveWorkspace` **نباید به existence oracle تبدیل شود**. یعنی نباید بشود با آن فهمید کدام organizationها در V1 وجود دارند.

پاسخ برای «پیوند ندارد» و «سازمان اصلاً وجود ندارد» باید از بیرون **یکسان** باشد — دقیقاً همان کاری که در مرز HTTP نسخه‌ی ۱ برای ۴۰۴ انجام شد و بازبینی مستقل روی درستی‌اش تاکید کرد.

## ۹. الزامات ممیزی

هر پیوند و هر تغییر وضعیت باید این‌ها را ثبت کند و **هیچ‌کدام اختیاری نیست**:

| فیلد | چرا |
|---|---|
| `linkedByActorId` | «چه کسی؟» |
| `linkedAt` | «کِی؟» |
| `basis` | «بر چه اساسی؟» — تایید مالک یا ثبت دستی |
| `revokedByActorId` + `revokedAt` | همان سه پرسش برای لغو |
| `note` | متن آزاد برای زمینه‌ی انسانی |

**رکورد لغوشده حذف نمی‌شود.** پیوند گذشته بخشی از تاریخچه‌ی حاکمیتی است: اگر کسی بپرسد «چرا این داده شش ماه پیش به آن کسب‌وکار نسبت داده شد؟»، جواب باید وجود داشته باشد.

**پیشنهاد:** رویداد پیوند و لغو در `EventLog` هم ثبت شود تا در همان جریان event-sourced موجود بنشیند. این نیاز به یک `domainTag` جدید دارد و **در دامنه‌ی این CCR نیست** — به‌عنوان یک پرسش باز در بند ۱۳ ثبت شده.

## ۱۰. رفتار همگام‌سازی

**هیچ همگام‌سازی داده‌ای وجود ندارد.** این عمدی است.

```
Content Studio  ──(workspace_id)──►  V1 Resolver  ──►  organization_id
```

- V1 داده‌ی Content Studio را نمی‌کشد.
- Content Studio داده‌ی V1 را ذخیره نمی‌کند — فقط در همان فراخوانی استفاده می‌کند.
- هیچ کار پس‌زمینه‌ای، هیچ webhook، هیچ صف رویدادی.

**چرا:** همگام‌سازی یعنی دو کپی و در نتیجه واگرایی. یک resolve در لحظه، همیشه تازه است.

**اگر V1 در دسترس نباشد:** Content Studio نباید حدس بزند و نباید مقدار کهنه استفاده کند. عملیاتی که به هویت نیاز دارد **متوقف می‌شود** با پیام صادقانه. این هزینه‌ی fail-closed است و پذیرفته می‌شود.

**Cache:** در V1 پیشنهاد نمی‌شود. اگر بعداً لازم شد، عمرش باید بسیار کوتاه باشد و لغو پیوند باید بی‌درنگ آن را باطل کند — که خودش یک تصمیم جداست.

## ۱۱. رفتار حذف و لغو پیوند

| رویداد | رفتار |
|---|---|
| **لغو پیوند** | `status = REVOKED` + بازیگر و زمان. رکورد **حذف نمی‌شود**. |
| **بلافاصله پس از لغو** | هر `resolveWorkspace` جواب «پیوند ندارد» می‌دهد. بدون دوره‌ی مهلت. |
| **داده‌ی تولیدشده پیش از لغو** | **دست‌نخورده می‌ماند.** لغو پیوند یعنی «از این پس نه»، نه «گذشته را پاک کن». |
| **حذف organization در V1** | همه‌ی پیوندهایش `REVOKED` می‌شوند. |
| **حذف workspace در Content Studio** | V1 خبردار نمی‌شود (بدون همگام‌سازی). پیوند `ACTIVE` می‌ماند ولی به چیزی اشاره نمی‌کند — resolve موفق است ولی خودِ workspace وجود ندارد. **این یک حالت شناخته‌شده است**، در بند ۱۳ ثبت شده. |

⚠️ **آنچه لغو پیوند انجام نمی‌دهد:** حذف داده. اگر داده‌ی محتوایی باید حذف شود، آن یک عملیات جداست با مجوز جدا — و برای داده‌ی مشتری، مسدود تا تصویب سیاست R8-a.

## ۱۲. ریسک‌های مهاجرت

| ریسک | شدت | کاهش |
|---|---|---|
| **ایندکس یکتای جزئی در Prisma بومی نیست** | متوسط | SQL خام در migration. باید با تست واقعی (نه فرض) اثبات شود که واقعاً اعمال شده. |
| **داده‌ی موجود هیچ پیوندی ندارد** | بالا | مهاجرت = **ثبت دستی و تاییدشده**. هیچ حدس خودکاری از روی نام. تا ثبت نشدن، همه‌چیز fail-closed است. |
| **فایل منجمد لمس می‌شود** | بالا | همین CCR. بدون تصویب، صفر تغییر. |
| **تعارض با کار در جریان دیگران** | متوسط | `implementation/` قلمرو یونس است، ولی migration روی دیتابیس مشترک اثر دارد؛ باید هماهنگ شود. |
| **مقدار enum جدید بعداً** | کم | `ExternalSystem` عمداً تک‌مقداری است — همان درس CR-02 که برای `OwnershipType` گرفته شد: تعمیم زودهنگام در سطح نوع، ممنوع. |
| **Adapter پیش از نگاشت ساخته شود** | متوسط | ترتیب مصوب نقشه‌ی راه این را از قبل می‌بندد. |

## ۱۳. راهبرد بازگشت (Rollback)

**پیش از هر داده‌ی واقعی** — یعنی وقتی جدول خالی است:

```sql
DROP TABLE external_workspace_links;
DROP TYPE  external_link_basis;
DROP TYPE  external_link_status;
DROP TYPE  external_system;
```

بازگشت کامل و بی‌هزینه. هیچ مدل موجودی تغییر نمی‌کند، پس هیچ چیز دیگری نمی‌شکند.

**پس از وجود داده‌ی واقعی:** جدول **حذف نمی‌شود**. به‌جایش همه‌ی پیوندها `REVOKED` می‌شوند و رابط resolve غیرفعال می‌گردد. سیستم به رفتار امروز برمی‌گردد (همه‌چیز fail-closed) ولی تاریخچه‌ی حاکمیتی حفظ می‌شود.

**چرا این نامتقارن است:** حذف جدولی که تاریخچه‌ی «چه کسی چه چیزی را کِی به چه کسی وصل کرد» دارد، همان ممیزی‌پذیری‌ای را از بین می‌برد که کل هدف این مدل بود.

**نقطه‌ی بی‌بازگشت:** اولین پیوند واقعی. پس از آن، بازگشت یعنی غیرفعال‌سازی، نه حذف.

## ۱۴. پرسش‌های باز — نیازمند تصمیم مالک

۱. **ثبت رویداد پیوند در `EventLog`؟** نیاز به `domainTag` جدید دارد و در دامنه‌ی این CCR نیست. ثبت جداگانه یا داخل همین جدول کافی است؟

۲. **حذف workspace در Content Studio چه شود؟** بدون همگام‌سازی، V1 خبردار نمی‌شود و پیوند به چیزی اشاره می‌کند که وجود ندارد. یک بررسی دوره‌ای می‌خواهیم، یا این حالت پذیرفته می‌شود؟

۳. **`SUSPENDED` واقعاً لازم است؟** حذفش مدل را ساده‌تر می‌کند. اگر سناریوی واقعی برایش نداریم، **توصیه‌ی من حذف آن است** — همان اصل پرهیز از تعمیم زودهنگام.

۴. **آیا `basis` باید مقادیر بیشتری داشته باشد؟** امروز دو تا: تایید مالک و ثبت دستی.
