# بازبینی هویت «وضعیت کسب‌وکار» Opportunity (R5)

**این سند یک تکلیف شفاف‌سازی است. طبق دستور صریح این اصلاح، هیچ کدی برای حل این مسئله نوشته نشد.**

## طرح مسئله

`opportunity_correlation_id` هویت خود را از `id` رویداد Occurrence بنیان‌گذارش می‌گیرد. اما کلید Idempotency (`unique_key`) شامل هش محتواست. پس اگر همان وضعیت واقعی کسب‌وکار (مثلاً «این Slot خالی، این تاریخ، این منبع») دوباره دیده شود اما Payload کمی متفاوت باشد (مثلاً `materiality_score` به‌روزشده)، ممکن است به‌جای AMENDMENT روی Opportunity موجود، یک **Occurrence بنیان‌گذار جدید و مستقل** ایجاد شود — چون هیچ کلید طبیعی مستقلی («هویت وضعیت کسب‌وکار») برای یافتن Correlation ID موجود وجود ندارد.

## نتیجه‌گیری

**CONTRACT_CHANGE_REQUEST REQUIRED.**

این مسئله را می‌توان **بدون** تغییر Kernel/ADR/IC (سطح معماری منجمد) حل کرد: مکانیزم پیشنهادی (زیر) کاملاً درون قلمروی «چگونه هر Value Engine داده‌ی خودش را پیگیری می‌کند» می‌ماند — دقیقاً مثل الگوی موجودِ `CancellationRepository.getUnprocessedCancellations` که از قبل نوعی ردیابی «قبلاً پردازش‌شده» را در سطح Repository (نه Kernel) پیاده می‌کند. بنابراین یک **ARCHITECTURE_CHANGE_REQUEST لازم نیست** — این یک شکاف در سطح **Phase 4A Feature Contract / Phase 4B Feature Package** است، نه در سطح Kernel/ADR.

پیشنهاد حداقلی برای CCR آینده (این تکلیف آن را نمی‌سازد یا اعمال نمی‌کند، طبق بند ۱۶ دستور — «هیچ موتور Dedup نساز»):
- هر Value Engine (F-01/F-02/F-03) مسئول نگه‌داشتن نگاشت خودش «کلید طبیعی وضعیت → آخرین `opportunity_correlation_id` شناخته‌شده» در Repository اختصاصی خودش می‌شود (نه یک سرویس Kernel-level جدید، نه یک Core Entity جدید، نه یک خانواده‌ی Event جدید).
- Feature Contract هر Value Engine باید صریحاً این کلید طبیعی را تعریف کند (مثلاً برای F-01: `{resourceRef, date}`).
- این پیشنهاد را باید فاز طراحی/بازبینی معماری (نه این اصلاح جراحی) رسمی و تصویب کند.

## وضعیت Wave 1 فعلی

**بدون تغییر در این اصلاح.** F-01/F-02/F-03 هم‌چنان همیشه `OCCURRENCE` تولید می‌کنند (رفتار از قبل موجود، حفظ‌شده، نه اصلاح‌شده و نه پنهان‌شده). این یک محدودیت شناخته‌شده است، نه یک باگ خاموش‌شده.
