# قوانین کنترل تغییر معماری و مرزهای عامل کارگر

**وضعیت: FORMALLY FROZEN (فاز ۳D).** این سند، همراه با `SOURCE_OF_TRUTH_MAP.md`، مرجع رفتاری هر Worker Agent آینده است.

---

## بخش ۱ — قاعده‌ی کنترل تغییر (Change Control Rule)

**اگر پیاده‌سازی یک تعارض با معماری منجمد آشکار کرد:**

> **هرگز به‌طور خاموش معماری منجمد را تغییر نده.**

به‌جای آن، یک **ARCHITECTURE_CHANGE_REQUEST** بساز، شامل:

1. تعارض کشف‌شده (دقیقاً چه چیزی، در کجا)
2. اقتدار متأثر (کدام Capability/ADR/IC)
3. اثر بر پیاده‌سازی (چه چیزی مسدود شده)
4. الحاقیه‌ی حداقلی پیشنهادی
5. گزینه‌های جایگزین بررسی‌شده
6. سازگاری با نسخه‌های قبلی
7. فوریت

**راحتی پیاده‌سازی، به‌تنهایی، دلیل کافی برای تغییر معماری منجمد نیست.** این دقیقاً همان انضباطی است که خود فاز ۳D رعایت کرد — هر الحاقیه (Kernel v1.3) با یک ADR رسمی، مقایسه‌ی گزینه‌ها، و رد صریح گزینه‌های نامناسب توجیه شد، نه صرفاً برای «راحت‌تر شدن» ساخته شد.

## بخش ۲ — الگوی ARCHITECTURE_CHANGE_REQUEST

فایلی با همین ساختار هفت‌بخشی بالا، در پوشه‌ای مشخص (مثلاً `ARCHITECTURE_CHANGE_REQUESTS/`) ثبت و برای بازبینی معمار ارشد/مالک محصول ارسال می‌شود — دقیقاً هم‌الگو با فرایندی که ADR-00AC/AD/AE و الحاقیه‌ی Kernel v1.3 خودشان طی کردند (فاز ۳B پیشنهاد → فاز ۳B/۳C بازبینی تخاصمی → فاز ۳C اصلاح → فاز ۳D تصویب و انجماد رسمی).

## بخش ۳ — مرزهای Worker Agent

### مجاز (MAY):

- پیاده‌سازی در برابر Feature Contractهای تعریف‌شده
- نوشتن تست بر اساس دسته‌های پذیرش تعریف‌شده (`opportunity_architecture/*_v2.md`)
- کار در محدوده‌ی دایرکتوری‌های تخصیص‌یافته
- استفاده از رابط‌های تأیید‌شده (IC-13، IC-14، و ۱۲ Interaction Contract پیشین)
- پیشنهاد بهینه‌سازی (در قالب ARCHITECTURE_CHANGE_REQUEST، نه تغییر مستقیم)

### غیرمجاز (MAY NOT):

- ویرایش `Kernel_Architecture_v1.3_FROZEN.md`
- ویرایش هر ADR پذیرفته‌شده (`governance/ADR-*`)
- ویرایش `Interaction_Contracts_v1.1_FROZEN.md`
- بازتعریف Opportunity (نوع، هویت، چرخه‌ی عمر)
- تغییر مالکیت Event Log (همیشه، منحصراً Capability «حافظه و دانش»)
- گسترش اقتدار دسترسی/مجوز (همیشه، منحصراً AC-2/Capability «اعتماد، توضیح‌پذیری و حاکمیت»)
- تغییر مرز V1/V2
- معرفی نوع جدید موجودیت Core (فقط `Individual`/`Interaction`، طبق ADR تأیید‌شده)
- معرفی وابستگی هوش مصنوعی پولی بدون توجیه صریح در بخش «اقتصاد اجرا» یک Feature Contract (طبق `opportunity_architecture/FEATURE_CONTRACT_EXECUTION_ECONOMICS_AMENDMENT.md`)
- فراخوانی IC-13 بدون ثبت پیشین در رجیستری تولیدکننده

## بخش ۴ — مرز Legacy Malino

**معماری منجمد > پیاده‌سازی.** کد Legacy Malino ممکن است REUSE، WRAP، ADAPT، MIGRATE، REPLACE، RETIRE، یا UNKNOWN طبقه‌بندی شود (`opportunity_architecture/LEGACY_HYBRID_BOUNDARY.md`) — هیچ‌کدام معماری را عوض نمی‌کند. **معماری هرگز صرفاً برای تطبیق با کد Legacy تغییر نمی‌کند.** بسته‌ی NestJS کشف‌شده‌ی فاز ۳A نیز، تا زمانی که منشأش مستقل تأیید نشود، فقط یک هدف استقرار احتمالی است، نه منبع معماری.

## بخش ۵ — مرز Adaptive Execution

اصل تصویب‌شده: **از ارزان‌ترین مسیر اجرایی که به‌طور معتبر ارزش موردنیاز مشتری را تحویل می‌دهد استفاده کن.** انتخاب مدل/ارائه‌دهنده هرگز وارد Kernel نمی‌شود. Commercial Plan ≠ Technical Execution Profile. Authorization ≠ Execution Routing. **هیچ انتخاب ارائه‌دهنده در فاز ۳D انجام نشد و نباید توسط هیچ Worker Agent بدون Feature Contract صریح انجام شود.**

## بخش ۶ — مرز V1/آینده

خارج از baseline منجمد (تا اطلاع ثانوی): تماس خودکار بیرونی، رابط صوتی، هوش رسانه‌ی اجتماعی، Content Copilot، تولید آواتار، OCR، اتوماسیون حسابداری/بیمه، پیگیری خودکار بیمار، شبکه‌ی Partner V2، هوش شبکه‌ای، تبادل Opportunity بین‌سازمانی. این baseline عمداً مسیر آینده به این‌ها را نمی‌بندد، اما آن‌ها را اکنون معماری نمی‌کند.
