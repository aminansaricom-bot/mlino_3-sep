# سند J — مرز Legacy/Hybrid

**وضعیت: PROPOSED — NOT YET FROZEN.** پوشش‌دهنده‌ی بخش ۲۲ فاز ۳B. HYBRID به معنای «حفظ همه‌ی کد Legacy» نیست — هر مؤلفه جداگانه طبقه‌بندی شده است.

---

## طبقه‌بندی کامل مؤلفه‌های Malino

| مؤلفه‌ی Legacy | طبقه‌بندی | دلیل |
|---|---|---|
| جداول `Appointment`، `WorkingHour`، `Patient`، `Clinic`، `Payment` | **REUSE** (به‌عنوان منبع Connector) | داده‌ی واقعی و معتبر؛ به‌جای بازسازی، از طریق یک Connector به Event Log جدید همگام می‌شود |
| `notify.js` / `telegram.js` | **WRAP** | مکانیزم تحویل واقعی و کارکرد را حفظ کن؛ فراخوانی مستقیم آن از منطق کسب‌وکار حذف و پشت قرارداد Capability ۷ (روایت) قرار می‌گیرد |
| `assistantTools.js` (جداسازی انتخاب/اجرای ابزار) | **ADAPT** | ساختار جداسازی واقعی و قابل‌استفاده است؛ اما مسیر اجرا باید از Capability ۶ (Self-Critique) و مجوز انسانی (ADR-00X) عبور کند — طبق یافته‌ی تأییدشده‌ی فاز ۳A |
| `managerAssistant.js` (حلقه‌ی فراخوانی مستقیم ابزار) | **ADAPT (اولویت بالا، ایمنی‌محور)** | همان فایل بالا؛ این دقیقاً محل نقض تأییدشده‌ی ADR-00X/ADR-00Z است — باید پیش از هرگونه گسترش قابلیت گفتگو اصلاح شود (سند H) |
| `ai.js` (دستیار پذیرش بیمار) | **REUSE** | فقط پرسش/پاسخ، بدون اجرای اقدام روی داده؛ خارج از مسیر مجوز انسانی، بدون تغییر لازم |
| `License`, `TRIAL_DAYS`, `signup-trial`, `expireLicenses.js` | **REUSE** | مستقیماً پشتیبان PD-V1-06؛ خارج از حوزه‌ی Kernel (§۲۱)، نیازی به تغییر معماری ندارد |
| مدل احراز هویت (سه دامنه‌ی JWT مجزا) | **REUSE** | با اصول جداسازی مستأجر Kernel §۱۸ سازگار است (طبق ارزیابی فاز ۳A) |
| `faceMatch.js`، `face-enroll.html`، `face-models/` | **UNKNOWN — نگه‌داری بدون گسترش** | طبق PD-V1-13، نه کار جدید نه حذف؛ در انتظار بازبینی مدل رضایت (Consent Model، Kernel §۱۱) |
| `aiProvider.js` (انتخاب DeepSeek/Groq/OpenRouter) | **REUSE** | نمونه‌ی واقعی و کارآمد اصل Adaptive Execution؛ می‌تواند مستقیماً به‌عنوان لایه‌ی اجرای پیش‌فرض هر Value Engینی که هوش مصنوعی نیاز دارد استفاده شود |
| ماژول‌های NestJS کشف‌شده (Memory & Knowledge، Domain Adaptation، Decision Support، Action & Execution، Trust & Governance) | **REUSE (مشروط به تأیید منشأ — تصمیم مالک محصول ردیف A در فاز ۳A)** | زیرساخت سازگار با Kernel و آزمایش‌شده؛ پایه‌ی پیشنهادی برای Event Log و اجرای IC-۱۳/IC-۱۴ |
| `dental-accounting.html` | **RETIRE از دامنه‌ی V1** (نه حذف کد) | طبق PD-V1-12، MLINO جایگزین حسابداری نمی‌شود؛ این صفحه فعلاً خارج از V1 Core باقی می‌ماند، بدون حذف از کد |
| کد فرانت‌اند فعلی (HTML ساده، بدون فریم‌ورک) | **MIGRATE (در آینده، نه اکنون)** | Feed و Opportunity Card جدید نیازمند رابط کاربری جدید هستند؛ این فاز طراحی نهایی UI را انجام نمی‌دهد (بخش ۱۴ فاز ۳B) |

## اصل حاکم بر این جدول

طبق بخش ۲۲ فاز ۳B: «معماری همچنان مرجع نهایی است. پیاده‌سازی Legacy شواهد و پیاده‌سازی بالقوه‌ی قابل‌استفاده است — نه خودِ معماری.» هیچ ردیف بالا به‌معنای «معماری این بخش را دیکته کرده» نیست؛ هر ردیف نتیجه‌ی اعمال معماری پیشنهادی این فاز روی شواهد واقعی کد است.

## نقطه‌ی یکپارچه‌سازی HYBRID (خلاصه)

```
داده‌ی Malino (Postgres موجود)
        ↓ (Connector، Capability ۸)
Event Log جدید (میزبانی‌شده در زیرساخت NestJS کشف‌شده، Capability ۱)
        ↓
Value Engine ها (ظرفیت/کنسلی/پیگیری) — می‌خوانند از Projection
        ↓ (IC-۱۳)
Opportunity Event ها
        ↓
Feed / Briefing / گفتگو (تحویل نقش‌آگاه، اسناد D/E)
```

`notify.js`/`telegram.js` موجود، به‌عنوان کانال تحویل واقعی Capability ۷ در همین زنجیره WRAP می‌شوند — بدون بازنویسی.

## آنچه باز (OPEN) باقی می‌ماند

- طراحی دقیق Connector بین Postgres موجود Malino و Event Log جدید — سطح API Design، نه این فاز.
- تأیید منشأ بسته‌ی NestJS کشف‌شده (تصمیم مالک محصول، ردیف A، بخش ۲۶ گزارش نهایی این فاز).
