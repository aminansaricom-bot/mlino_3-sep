# پیش‌نویس قرارداد یکپارچگی V1 ↔ V2 (Business Directory Sync)

**وضعیت: DRAFT / پیشنهادی.** این سند یک قرارداد منجمد نیست — چون سمت V1 آن (فهرست محصولات کسب‌وکار) هنوز اصلاً ساخته نشده. هدف این سند این است که موجی از همین ابتدا با **یک شکل داده‌ی مشخص و باثبات** کار کند، به‌جای اینکه بعداً مجبور شود همه‌چیز را بازنویسی کند. وقتی V1 واقعاً این قابلیت را ساخت، این سند باید با یونس (تیم V1) تطبیق داده و نهایی شود.

## ۱. اصل طراحی

انتقال داده همیشه **یک‌طرفه و فقط‌خواندنی** است: V1 → V2. V2 هرگز به V1 چیزی «می‌نویسد» — این دقیقاً همان اصل «Producer ≠ Event Log Owner» و «فقط‌خواندنی بودن اتصال V2» است که در معماری V1 از قبل جا افتاده.

## ۲. شکل پیشنهادی «پروفایل کسب‌وکار» (Business Directory Record)

```json
{
  "business_id": "string — شناسه‌ی پایدار کسب‌وکار در V1",
  "organization_id": "string — همان organization_id که در V1 استفاده می‌شود",
  "name": "string",
  "category": "string — مثلا 'dental_clinic', 'beauty_clinic', 'cafe', 'restaurant', 'retail_shop'",
  "location": {
    "latitude": "number",
    "longitude": "number",
    "floor_level": "number | null — طبقه، اگر داخل یک ساختمان چندطبقه است",
    "building_id": "string | null — شناسه‌ی اختیاری ساختمان/پاساژ/مال، برای گروه‌بندی چندطبقه"
  },
  "products": [
    {
      "product_id": "string",
      "name": "string",
      "description": "string | null",
      "price": "number | null",
      "currency": "string | null",
      "image_url": "string | null",
      "is_active": "boolean"
    }
  ],
  "offers": [
    {
      "offer_id": "string",
      "title": "string",
      "description": "string | null",
      "discount_percent": "number | null",
      "valid_from": "ISO timestamp",
      "valid_until": "ISO timestamp | null"
    }
  ],
  "last_synced_at": "ISO timestamp — آخرین باری که این رکورد از V1 به‌روزرسانی شد"
}
```

**نکات:**
- این شکل داده **در V1 امروز وجود ندارد** — نه `products`، نه `offers`، نه `floor_level`. این‌ها باید در آینده به‌عنوان یک Feature جدید در V1 ساخته شوند.
- تا وقتی V1 این داده را واقعاً تولید نمی‌کند، موجی باید از **داده‌ی آزمایشی/Mock با همین دقیق شکل** استفاده کند — نه شکل دیگری — تا وقتی V1 آماده شد، فقط منبع داده عوض شود، نه کل مدل.

## ۳. مکانیزم انتقال پیشنهادی (برای آینده، نه اکنون)

سه گزینه، به ترتیب اولویت پیشنهادی — انتخاب نهایی باید وقتی V1 این Feature را ساخت، مشترکاً تصمیم‌گیری شود:

1. **API فقط‌خواندنی** — V1 یک Endpoint فقط‌خواندنی (`GET /v1/business-directory-export`) ارائه می‌دهد که V2 دوره‌ای Poll می‌کند.
2. **فایل Export دوره‌ای** — V1 یک Snapshot دوره‌ای (JSON/CSV) تولید می‌کند که V2 وارد می‌کند — ساده‌تر برای شروع، مناسب فاز اول.
3. **رویداد آسنکرون** — اگر حجم و تعداد به‌روزرسانی زیاد شد، یک صف پیام (Webhook/Event) — این را فقط وقتی به آن نیاز واقعی داشتیم اضافه کنیم (طبق همان انضباط V1: زیرساخت جدید فقط وقتی که واقعاً لازم است، نه پیش‌دستانه).

**برای شروع کار موجی: گزینه‌ی ۲ (فایل Export دوره‌ای با داده‌ی Mock) کافی و توصیه‌شده است.**

## ۴. مسئولیت هرکدام

| مسئولیت | طرف |
|---|---|
| تولید و صحت داده‌ی کسب‌وکار (پروفایل/محصول/آفر) | **V1 (آینده)** |
| ذخیره‌ی Cache خواندنی این داده در V2 | **V2** |
| منطق تطبیق نیاز مشتری با محصولات | **V2** |
| رندر نقشه/AR | **V2** |
| هرگونه نوشتن/تغییر داده‌ی کسب‌وکار | **فقط V1 — V2 هرگز** |

## ۵. اقدام لازم برای نهایی‌شدن این قرارداد

وقتی V1 واقعاً کار روی «فهرست محصولات کسب‌وکار» را شروع کرد، این سند باید توسط یونس (تیم V1) بازبینی و با شکل واقعی داده‌ی V1 تطبیق داده شود — قبل از آن، این سند فقط یک **فرضیه‌ی کاری** برای موجی است، نه یک قرارداد منجمد نهایی.
