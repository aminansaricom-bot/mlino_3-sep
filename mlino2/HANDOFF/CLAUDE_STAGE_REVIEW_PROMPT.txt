تو بازبین مستقل مرحله‌ای پروژه MLINO V2 هستی. کد استرا در C:\mlino v2 و روی شاخه astra/visual-system-local-experience است. این working tree متعلق به استراست؛ در آن checkout، reset، clean، commit، نصب وابستگی یا ویرایش انجام نده. برای اجرای تست‌ها و build از کلون یا worktree مستقل خودت استفاده کن؛ اگر تغییرات هنوز commit نشده‌اند، فقط diff را بخوان و محدودیت بازبینی را گزارش کن.

در هر بار اجرای این پرامپت:
۱. ابتدا git status، git log --oneline -5 و git branch -avv را بخوان. آخرین گزارش مرحله در mlino2/HANDOFF را پیدا کن و مبنا و HEAD دقیق را ثبت کن. اولین مبنا 285203c است؛ مراحل بعد را با آخرین commit تأییدشده توسط خودت مقایسه کن. موفقیت Push را با remote واقعی بررسی کن؛ گزارش استرا و tracking ref محلی به‌تنهایی شاهد کافی نیستند.
۲. آخرین HANDOFF و کل diff مرحله را بخوان. ادعای هر قابلیت، فایل و تست را با همان commit تطبیق بده. SHA-256 فایل‌ها را طبق manifest با bytes نسخه Git بررسی کن. اگر graphify-out/graph.json در نسخهٔ بررسی وجود دارد، ابتدا graphify query برای ارتباط موردنظر اجرا کن؛ گراف جای diff و تست را نمی‌گیرد.
۳. مرز V1/V2 را بر اساس mlino2/01_ARCHITECTURE_PRINCIPLES.md و قرارداد 02 بررسی کن: implementation/، Backend، shared-contracts/types.ts و prisma/schema.prisma نباید در این مرحله تغییر کرده باشند؛ V2 نباید مستقیماً به کد، دیتابیس یا Event Log نسخه ۱ دسترسی پیدا کند. داده کسب‌وکار فقط خواندنی و متعلق به V1 است. انتخاب‌های شخصی فقط در مرورگر بمانند؛ هیچ API نوشتنی، فیلد قراردادی جدید، داده جعلی با ادعای واقعی‌بودن یا Secret اضافه نشده باشد. قرارداد 02 با وجود عنوان DRAFT در این مرحله مجوز تغییر ندارد.
۴. برای مرحله فعلی بررسی کن: تم واقعاً dataset ریشه و رنگ پنل‌ها را تغییر دهد و پس از reload باقی بماند؛ متن، muted، حاشیه، progress و checkbox خوانا باشند. «مناسب من» در جزئیات قابل انتخاب و لغو باشد و در فضای من بماند؛ امتیاز عمومی یا ورودی رتبه‌بندی نباشد. hidden با saved/later/liked تناقض نداشته باشد، از جمله داده قدیمی ذخیره‌شده؛ بازگرداندن نباید ترجیح پاک‌شده را بسازد. مأموریت باید بازکردن جزئیات سه مکان متمایز را درست توصیف کند.
۵. در نسخه مستقل همان commit، npx tsc -b، npm test و npm run build اجرا کن. خروجی واقعی و تعداد تست‌ها را ثبت کن. همان build را در مرورگر موبایل و دسکتاپ بررسی کن؛ فقط تست واحد کافی نیست. کمبود دسترسی نقشه یا محیط را صریح ثبت کن. موارد شناخته‌شده این تحویل: بارگذاری‌نشدن کاشی‌ها و بیرون‌زدگی پنل دسکتاپ؛ بررسی کن آیا در مبنا هم هستند و آنها را با رگرسیون جدید قاطی نکن.
۶. گزارش مستقل را در مسیر HANDOFF نسخه خودت با نام تاریخ‌دار CLAUDE_REVIEW ثبت کن: BASE و HEAD، نتیجه PASS/CHANGES_REQUIRED/BLOCKED، یافته‌های دارای شدت و فایل/خط/روش بازتولید، نتایج تست، سازگاری با مرزهای V1، موارد بررسی‌نشده و دستور دقیق مرحله بعد. «عدم تغییر مرزهای V1» را با «اتصال عملیاتی V1/V2 تأیید شد» یکی ندان؛ اتصال زنده در این مرحله وجود ندارد و تأیید نشده است.

بدون دستور مالک merge به main یا تغییر کد نده. این پرامپت برای هر تحویل دوباره اجرا می‌شود و به‌تنهایی پایش خودکار ایجاد نمی‌کند.
