## ۳. بازخوانی فنی (نقاط قوت)

1. **قرارداد اعتبارسنجی مشترک (`intentContract.ts`):** خروجی هر دو موتور از همان `validateParsedIntent` سخت‌گیرانه رد می‌شود — ضدتوهم، لایه‌ای در سطح قرارداد است نه ادعا. تست «hallucinated category رد و fallback می‌شود» این را قفل کرده. ✅
2. **Edge-first واقعی:** `resolve` اول پارسر محلی را اجرا می‌کند؛ فقط وقتی کافی نبود (دسته null) به LLM می‌رسد — جواب کافی محلی = صفر فراخوانی شبکه (تست‌شده). ✅
3. **Fallback قطعی چهار‌سناریویی:** بدشکل/توهم/خطا/timeout → قاعده‌محور با `fellBackToRule=true` + ثبت مسیر در UI («موتور: LLM (model)» یا «fallback») — شفافیت کامل، جعبه‌سیاه نیست. ✅
4. **مسیریابی پلن‌آگاه:** `PLAN_ROUTES` داده‌ی قابل‌تعویض است، کلیدها صریحاً `plan_mock_*` (تست قفل کرده که همه شامل mock باشند) — هیچ پلن جعلی‌ای که بعداً «واقعی» جا بخورد. ✅
5. **کلید فقط در هدر HTTP** (نه URL که ممکن است لاگ بماند) — جزئیات امنیتی ظریف و درست. ✅
6. **گزارش هم‌ترازی 6500863:** ترتیب Provider برعکس بود (پیش‌فرض DeepSeek، رزرو Gemini) — با بند ۲.۲ دستور من اصلاح شد: Gemini Flash = مسیر روزمره‌ی پیش‌فرض، DeepSeek = رزرو تحلیلی. اصلاح + قفل با تست. ✅

## ۵. یافته‌ها (غیرمسدودکننده)

- **L-1 (INFO):** اعمال پلن سمت کلاینت = UX نه امنیت — صریحاً در سه نقطه (کامنت کد + گزارش + UI) ثبت شده؛ قفل واقعی فقط با Backend آینده. بدون اقدام — فقط یادآوری که این گپ کماکان باز است.
- **L-2 (INFO):** متغیر env مرورگر (`import.meta.env`) در build نهایی **داخل باندل قابل‌خواندن است** — یعنی کلیدی که در build فرانت‌اند قرار بگیرد عملاً عمومی است. وقتی اتصال زنده شد، کلیدها باید از یک Backend/SERVER-side proxy رد شوند، نه از باندل مرورگر. این در معماری فعلی (بدون Backend) فقط با استفاده‌ی محلی/دستی منطقی است — برای تصمیم Deploy آینده ثبت شود.
- **L-3 (INFO):** DeepSeek فعلاً «رزرو بدون مصرف‌کننده» است — Dead-config نیست (طبق استدلال موجی، داده‌ی خالص است) ولی وقتی مالک کاربرد تحلیلی واقعی برایش تعریف کرد، باید مصرف‌کننده‌اش با مجوز و بازبینی بیاید.
