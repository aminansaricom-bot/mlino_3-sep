# پاسخ کلاد — CR «پیشنهاد ساعتی و حباب زنده در نقشه و AR»

**تاریخ:** ۱۱ سپتامبر ۲۰۲۶
**نویسنده:** کلاد (Claude Opus 5) — پاسخ به [`20260908_CR_LIVE_OFFER_PULSE_FOR_CLAUDE.md`](20260908_CR_LIVE_OFFER_PULSE_FOR_CLAUDE.md)
**مبنا:** فقط تصمیم‌ها و ADRهای **مصوب** — D-52 · D-53 · D-56 · D-61 · D-64 · D-67 · D-68 · ADR-0010 · ADR-0012. **هیچ تصمیم تازه‌ای در این پاسخ ساخته نشده است.** جایی که تصمیم مصوبی وجود ندارد، صریحاً «باز» علامت خورده و به تصمیم باز مربوطش ارجاع شده است.

---

## خلاصه

**مسیر این CR: «CR قراردادی/Backend» — نه Frontend-only.**

- **«پیشنهاد ساعتی» یک موجودیت تازه نیست — یک آفر است** با بازه‌ی اعتبار کوتاه:
  - D-53: «موقت» بُعد است، نه شکل
  - D-68: آفر موجودیت Core و نسخه‌دار است
  - پس `LiveOfferEvent` جداگانه لازم نیست — نمایش دوم از یک مفهوم می‌شد.
- **آفر واقعی فقط وقتی به V2 می‌رسد** که:
  1. سمت V1 آفر و **مسیر انتشار** را داشته باشد (D-52 · D-53 · D-61)
  2. بخش آفر قرارداد `02` از راه **OD-05** تصویب شود
- **امروز هیچ‌کدام وجود ندارد.** طبق بازبینی راهبردی (`mlino_book/MLINO_POST_ARCHITECTURE_STRATEGY_REVIEW.md`، نقطه‌ی عطف N5)، ساخت این قابلیت **پس از** حداقل مسیر انتشار V1 است.
- **تصمیم اجرایی استرا درست بود و پابرجا می‌ماند:** هیچ فیلد تازه، هیچ API تازه، هیچ رویداد ساختگی. UI فقط آفرهایی را نشان می‌دهد که در رکورد واقعی دایرکتوری هستند.

## پاسخ شش پرسش

### ۱. قرارداد V1/V2 یا API مستقل؟

**قرارداد V1/V2 — از همان دروازه‌ی AC-2. نه API مستقل.**
- «هیچ مصرف‌کننده‌ای مستقیم از جدول نمی‌خواند. AC-2 تنها دروازه است» (نقشه‌ی راه، گام ۴). یک API موازی مخصوص آفر زنده، دروازه‌ی دوم می‌ساخت.
- **نگاشت بخش آفر از قبل تعیین شده است** (D-53، ثبت‌شده روی OD-05):
  - `offers[]` ← آفر با شکل کمپین
  - **`appliesTo`** ← ارجاع موضوعی
  - `discount_percent` ← `adjustment` کلی‌تر
  - **`is_active` ← حذف** — حضور در تصویر منتشرشده = «منتشرشده و معتبر»
- فیلدهای پیشنهادی CR با آفر D-53 منطبق‌اند:
  - `offer_id` ← شناسه‌ی پایدار
  - `starts_at` / `expires_at` ← بازه‌ی اعتبار
  - `status: cancelled` ← **پس گرفتن**
- **D-52 شرط می‌گذارد:** هر سازوکار انتقال باید **پس گرفتن را هم منتقل کند، نه فقط افزودن را.**

### ۲. `visibility_radius_meters` — تصمیم کسب‌وکار یا سیاست محصول؟

**باز — هیچ تصمیم مصوبی این را تعیین نکرده است.** این پاسخ تعیینش نمی‌کند. دو قید مصوب مرزش را روشن می‌کنند:
- **شرایط آفر مال V1 است؛ V2 شرطی اختراع یا شخصی‌سازی نمی‌کند** (D-53 قاعده‌ی ۹)
- **ربط و رتبه‌بندی مال V2 است** (D-52 بند ۸)

**پرسشی که باید پاسخ داده شود:** آیا شعاع نمایش یک **شرط آفر** است (مال کسب‌وکار) یا یک **قاعده‌ی ربط** (مال V2)؟ ← **OD-05**. تا تصمیم: **بدون این فیلد.**

### ۳. رضایت یا تنظیم جداگانه‌ی موقعیت کاربر؟

**باز — به OD-01 (سیاست رضایت) مربوط است.** موقعیت کاربر نهایی داده‌ی شخصی است و قاعده‌ی مصوب برای پردازش آن وجود ندارد. آنچه از تصمیم‌های مصوب می‌آید:
- دستیار مشتری بافت سازمانی ندارد و فقط حقیقت منتشرشده را می‌بیند (D-67 · ADR-0012)
- ذخیره یا شخصی‌سازی بر پایه‌ی داده‌ی کاربر پشت **OD-01** است (ADR-0012، بخش اجرا)

این پاسخ فراتر از این نمی‌رود.

### ۴. TTL، cache و قطع اینترنت

**قاعده از تصمیم‌های مصوب می‌آید. عددها جزئیات پیاده‌سازی V2‌اند:**

- **آفر پس از `expires_at` هرگز نمایش داده نمی‌شود** — انقضا خودکار است (D-53 قاعده‌ی ۷)
- **اگر اعتبار را نمی‌توان تایید کرد** (cache کهنه، قطع اینترنت): **fail-closed — پنهان.**
  - D-56: «منقضی ⇒ نامعلوم»
  - اصل «هرگز حدس نزن»
- **پس گرفتن** (`cancelled`) باید دست‌کم هم‌سرعت با افزودن برسد (D-52)
- خودکارسازی فقط در جهت بستن است (ADR-0010 تصمیم ۶) — پنهان کردن خودکار مجاز است، **نمایش دوباره‌ی خودکارِ آفری که اعتبارش تایید نشده، نه**

### ۵. انیمیشن — عملکرد موبایل و دسترس‌پذیری

**تصمیم UX مال V2 است** — رندر تجربه مال V2 است (D-64 · ADR-0012). دو قید معماری:

- **انیمیشن مشتق یک آفر منتشرشده و معتبر است و خودش داده نمی‌سازد** — همان اصلی که استرا گذاشت
- **«زنده» نباید وعده‌ی دسترس‌پذیری بدهد** (D-56: «دسترس‌پذیری وعده نیست — فقط رزرو وعده است»)
  - معتبر بودن یک آفر ≠ «الان جا دارند»
  - متن و نشانه‌ی بصری نباید «همین حالا در دسترس» را القا کنند

### ۶. تعارض با قرارداد `02` یا قراردادهای منجمد؟

- **با قراردادهای منجمد V1: تعارضی نیست** — `shared-contracts/types.ts` قرارداد داخلی V1 است و آفر در آن نیست.
- **با قرارداد `02`:** `02` هنوز **DRAFT** است (OD-05). بخش `offers` امروزش (`discount_percent` · `valid_from` · `valid_until`) طبق D-53 باید بازنگری شود.
- **تغییر رسمی لازم:** **CR روی بخش آفر قرارداد `02`، ذیل OD-05، طبق نگاشت D-53** — نه فیلد تازه‌ی مستقل.

## یک اصلاح لازم در V2 — پیش از آفر واقعی

`mlino2/app/src/matching/MatchingService.ts:91-93` **اولین آفر منقضی‌نشده‌ی رکورد** را به هر تطبیقی می‌چسباند — بدون `valid_from` و بدون ارجاع موضوعی (`appliesTo`).
- **با داده‌ی آزمایشی مشکلی نیست.**
- **پیش از مصرف آفر واقعی V1 باید با D-53 هم‌تراز شود** — هر دو شرط زمان، و ارتباط آفر با همان محصول یا خدمت تطبیق‌داده‌شده.
