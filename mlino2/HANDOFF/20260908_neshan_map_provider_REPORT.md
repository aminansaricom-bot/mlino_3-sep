# گزارش تحویل — جایگزینی سرویس نقشه با نشان (رفع مشکل ظاهر نقشه)

**تاریخ:** ۸ سپتامبر ۲۰۲۶ · **نویسنده:** یونس (Claude) · **مجوز:** دستور مستقیم مالک محصول

## ۱. مسئله

مالک محصول گفت ظاهر نقشه مشکل اصلی است و باید شبیه اسنپ/تپسی شود. تشخیص با شواهد:
سبک پیش‌فرض OSM («Mapnik») برای اپ مصرف‌کننده‌ی فارسی مناسب نیست — جاده‌های اشباع و
مهم‌تر، **پلاک شماره‌ی راه** (۱۶۰۵، ۱۹۳۵، ۱۷۵…) که داخل خودِ پیکسل کاشی پخته شده.

## ۲. بررسی گزینه‌ها — با آزمایش واقعی، نه فرض

| سرویس | برچسب فارسی | استایل تمیز | نتیجه |
|---|---|---|---|
| OSM (قبلی) | ✅ | ❌ | ۵.۳ ثانیه، شلوغ |
| CARTO Positron/Voyager | ✅ | ✅ | ❌ کد ۲۰۰ می‌داد ولی **روی تصویر watermark «API KEY REQUIRED»** بود |
| Esri Light Gray | ❌ | ✅ | لایه‌ی برچسبش برای تهران **۸۷۲ بایت = خالی** |
| Esri Street | ✅ | ❌ | از OSM بهتر نبود |
| Wikimedia | — | — | HTML برگرداند |
| فیلتر CSS روی OSM | — | جزئی | رنگ را ملایم می‌کند اما پلاک‌ها داخل تصویرند |
| **نشان** | ✅ | ✅ | **انتخاب‌شده** |

**درس روش‌شناختی:** وضعیت `200` گمراه‌کننده بود. فقط با نگاه‌کردن به خودِ تصویرِ کاشی
معلوم شد CARTO کلید می‌خواهد. اگر به کد وضعیت اکتفا می‌کردم، اشتباه انتخاب می‌کردم.

## ۳. چرا این «مهاجرت کتابخانه» نیست

قید مالک محصول: «مهاجرت کامل کتابخانه بدون تأیید انجام نشود.»
**SDK نشان خودش روی همان Leaflet 1.9.4 ساخته شده** — همان کتابخانه‌ای که از قبل داشتیم.
تنها تغییر: در `MapView.tsx` به‌جای `react-leaflet` از Leaflet به‌صورت امری استفاده شد،
چون `L.Map` نشان کلید را به‌عنوان option می‌گیرد و `key` در React یک prop رزرو‌شده است
و هرگز به سازنده نمی‌رسد. `react-leaflet` **فقط در همین یک فایل** استفاده می‌شد.

## ۴. تفکیک کلیدها — نکته‌ی امنیتی مهم

نشان دو نوع کلید دارد و این تفاوت حیاتی است:

- **`service.*`** — وب‌سرویس‌ها (مسیریابی، جست‌وجو، Geocoding). **هرگز سمت کلاینت نیاید**؛
  هرکس باندل را باز کند می‌تواند سهمیه را خرج کند. مالک محصول اول این نوع را داد و
  تشخیص داده شد که برای نمایش نقشه کار نمی‌کند.
- **`web.*`** — نمایش نقشه در مرورگر، **محدود به دامنه**. حضورش در باندل طبق طراحی خودِ
  نشان بی‌خطر است. همین استفاده شد.

**راهی که عمداً نرفتم:** می‌شد Static API را به‌عنوان منبع کاشی جا زد (هر کاشی = یک
فراخوانی). کار می‌کرد، اما هر بار باز شدن نقشه ≈ ۲۴ فراخوانی — سوءاستفاده از سرویسی
که برای این ساخته نشده و سوزاندن سریع سهمیه.

## ۵. تغییرات

| فایل | چه شد |
|---|---|
| `src/components/MapView.tsx` | بازنویسی روی SDK نشان (امری، همان Leaflet) |
| `src/neshan-leaflet.d.ts` | **جدید** — تایپ‌ها؛ عمداً `any` نگذاشتم، از `@types/leaflet` موجود استفاده شد |
| `.env.example` | **جدید** — فقط نام متغیرها، بدون مقدار |
| `.npmrc` | **جدید** — رجیستری نشان (کلیدی داخلش نیست) |
| `Dockerfile` | کلید نقشه از `ARG`؛ `.npmrc` پیش از `npm ci` |
| `docker-compose.yml` | کلید از env میزبان، نه Commit |
| `.dockerignore` | استثنای `!.npmrc` |

**درباره‌ی `.dockerignore`:** موجی درست تصمیم گرفته بود `.env*` از image بیرون بماند
(الزام L-2). آن قاعده برای کلیدهای LLM و `service.` **پابرجاست** — فقط کلید `web.` نقشه
از مسیر `ARG` می‌آید، چون جنسش عمومی است. اگر ARG داده نشود، اپ ساخته می‌شود ولی نقشه
**صادقانه حالت خطا** می‌دهد، نه نقشه‌ی خالیِ بی‌توضیح.

## ۷. محدودیت باقی‌مانده — صادقانه

در **محیط پیش‌نمایش من**، ۱۷ کاشی از ۳۲ با `ERR_CONNECTION_CLOSED` شکست خورد، در حالی
که `curl` همان URLها را ۲۰۰ می‌گیرد و هر چهار زیردامنه‌ی `tile1..4.neshan.org` سالم‌اند
(۲–۳ ثانیه). به‌احتمال زیاد پروکسی همین ماشین است، نه اپ یا نشان.

**نمی‌توانم این را از اینجا قطعی کنم — تست گوشی روی Container، آزمون واقعی است.**
اگر روی گوشی هم تکه‌های سفید دیدی، باید دنبال محدودیت دامنه‌ی کلید یا شبکه بگردیم.
