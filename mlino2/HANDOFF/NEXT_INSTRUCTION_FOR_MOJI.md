# پیام برای موجی — دستور ادامه: پیاده‌سازی LlmIntentParser (Dual-Provider) + گزارش تست میدانی

**تاریخ:** ۶ سپتامبر ۲۰۲۶
**نویسنده:** ممد (بازبین مستقل V2، GLM 5.3 Flash) — بر پایه‌ی دو تصمیم مصوب مالک محصول (سرویس LLM + پلن‌بندی/Edge-first) و نتیجه‌ی بازبینی HTTPS (`20260906_MAMAD_INDEPENDENT_REVIEW_HTTPS_FIELDTEST.md`)
**وضعیت گزارش‌های قبلی:** پابرجا — M-1، I-1، A-1، A-2، V2-1 تا V2-5 همگی معتبر. این سند دستور فعال بعدی توست.

## ۱. نتیجه‌ی آخرین بازبینی (برای اطلاع)

- **قابلیت `dev:https` تایید شد** (بازبینی مستقل: ۵۵/۵۵ مستقل + اجرای واقعی HTTPS با curl → 200). یادداشت حاکمیتی: تفسیر کم‌ریسک تو از «شروع کن» این بار Pass شد — اما دفعه‌ی بعد اگر مشخص نبود، بپرس. (V2-4 جدید: بعد از تست میدانی، گزارش دستگاه/مرورگر/رفتار A-1 را ثبت کن.)
- V2-1 (پیش‌نیاز Secure Context) اکنون برطرف است — ابزار تست میدانی آماده است.

## ۲. دستور فعال: پیاده‌سازی `LlmIntentParser` — با هر دو مدل مصوب

چراغ سبز قبلی پابرجاست (سند ۱۹e7c8a). **نکته‌ی جدید: کلیدهای API هنوز از مالک نیامده‌اند — پس این پاس را کاملاً Mock/Config-محور بساز و آماده‌ی اتصال تحویل بده.**

### ۲.۱. الزامات (پنج الزام قبلی + سه تکمیلی — همه پابرجا)

1. **Interface:** `LlmIntentParser implements` همان قرارداد `ParsedIntent` — هیچ مسیر داده‌ی جدیدی نه.
2. **ضدتوهم:** خروجی LLM فقط پارامتر جست‌وجوست؛ باید از همان اعتبارسنجی رد شود (دسته از `KNOWN_CATEGORIES`، شعاع عددی، keywords از توکن‌های واقعی جمله). نتیجه همیشه از `BusinessDirectoryService`. LLM هرگز کسب‌وکار/محصول نمی‌سازد.
3. **Fallback قطعی:** API نبود/خطا/پاسخ نامعتبر → خودکار `RuleBasedIntentParser` — دستیار هرگز از کار نمی‌افتد. مدل + نسخه‌ی استفاده‌شده در هر پاسخ ثبت شود (شفافیت، نه جعبه‌سیاه).
4. **حریم خصوصی:** جمله‌ی کاربر بدون هیچ شناسه به API بیرونی می‌رود؛ در گزارش صریح. **کلیدها فقط `env` — هرگز در ریپو/Commit/تست.**
5. **تست:** قرارداد مشترک هر دو پیاده‌سازی (rule-based + LLM)؛ Adapter LLM فقط با Mock API (بدون شبکه‌ی واقعی در تست)؛ تست fallback؛ build سبز.
6. **مسیریابی پلن‌آگاه (config):** نگاشت «پلن/کاربرد → مدل» داده‌ی قابل‌تغییر در config، نه کد سخت. ساختار واقعی پلن‌ها هنوز نیامده — **هیچ پلن جعلی تعریف نکن** (نمونه‌ی تستی صریحاً «آزمایشی»).
7. **Edge-first:** قاعده‌محور پیش‌فرض و روی دستگاه؛ LLM فقط وقتی قاعده‌محور کافی نبود یا پلن/کاربرد ایجاب کرد. در گزارش صریح: چه‌چیزی روی دستگاه است، چه‌چیزی شبکه‌ای.
8. **محدودیت صادقانه الزامی:** بدون Backend، اعمال پلن سمت کلاینت = UX نه امنیت — هیچ ادعای قفل واقعی.

### ۲.۲. Dual-Provider — نگاشت کاربرد به مدل (تصمیم مصوب مالک: DeepSeek و Gemini Flash «بسته به کاربرد»)

- هر دو Adapter را بساز (هر دو Provider در config قابل‌انتخاب) — انتخاب پیش‌فرض این‌طور پیشنهاد می‌شود و می‌توانی با استدلال تغییرش دهی (مستند کن):
  - **Gemini Flash:** فهم نیت روزمره (سریع/ارزان) — مسیر پیش‌فرض پلن‌های دارای LLM.
  - **DeepSeek:** کاربرد تحلیلی/پیچیده‌تر (وقتی لازم شد) — رزرو.
- این «تقسیم کار» فعلاً فقط در لایه‌ی config + مستندسازی است؛ هیچ مصرف‌کننده‌ی جدیدی برای DeepSeek لازم نیست این پاس.

### ۲.۳. ممنوع‌ها

- هیچ کلید API در ریپو/Commit/لاگ؛ هیچ فراخوانی شبکه‌ی واقعی در تست.
- V1 دست‌نخورده (تشخیص قطعی فرصت‌ها همیشه بدون LLM — اصل منجمد). قرارداد `02` دست‌نخورده.
- هیچ ساختار پلن واقعی؛ هیچ Backend جدید؛ هیچ کار Connector/V1.

## ۳. گزارش تست میدانی (پارالل — مستقل از بند ۲)

طبق V2-4: وقتی تست میدانی روی گوشی واقعی انجام شد (چک‌لیست گزارش HTTPS)، نتایج را در `mlino2/HANDOFF/` ثبت کن: دستگاه/مرورگر، بج قطب‌نما (absolute یا نه)، رفتار M-1/A-1 روی دستگاه، چیزهای غیرمنتظره. این خروجی، ورودی تصمیم‌های مالک است.
