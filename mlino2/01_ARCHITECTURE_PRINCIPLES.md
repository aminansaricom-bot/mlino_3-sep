# MLINO V2 — اصول معماری الزامی برای موجی

این سند چارچوب مهندسی است که هر خط کد V2 باید طبقش پیش برود. هدف: V2 از روز اول طوری ساخته شود که (الف) مستقل و قابل‌توسعه باشد، (ب) هرگز مستقیماً به داخل V1 دست نبرد، (ج) در آینده با حداقل بازنویسی به V1 وصل شود.

## ۱. قاعده‌ی طلایی — مرز V1/V2 هرگز نقض نشود

- **V2 هرگز مستقیماً به پایگاه‌داده، کد، یا Event Log واقعی V1 دسترسی ندارد.** تنها راه ارتباط، یک قرارداد داده‌ی صریح و نسخه‌بندی‌شده است (`02_V1_V2_INTEGRATION_CONTRACT_DRAFT.md`).
- **مالکیت داده‌ی کسب‌وکار همیشه با V1 می‌ماند.** V2 فقط یک **کپی/Cache خواندنی** از داده‌ی کسب‌وکار (پروفایل، محصولات، آفرها، موقعیت) نگه می‌دارد — هرگز منبع حقیقت آن نیست.
- **V2 هرگز برای پرکردن یک شکاف V1 استفاده نمی‌شود** — اگر V1 چیزی ندارد (مثلاً فهرست محصولات، که امروز اصلاً وجود ندارد)، V2 نباید آن را جعل یا حدس بزند؛ باید صریحاً به‌عنوان «در انتظار V1» علامت بخورد.
- **کلمه‌ی «Opportunity» در V2 معنای متفاوتی از V1 دارد** — در V1 یعنی یک رخداد داخلی کسب‌وکار (ظرفیت خالی و مشابه)؛ اگر در V2 هم از این کلمه استفاده می‌شود (مثلاً «فرصت تطبیق نیاز مشتری»)، باید همیشه با پیشوند/زمینه‌ی روشن (`v2_match_opportunity` یا مشابه) از مفهوم V1 متمایز بماند — هرگز در یک جدول/API مشترک قاطی نشوند.

## ۲. معماری پیشنهادی (لایه‌بندی)

```
┌─────────────────────────────────────────────┐
│  V2 Client Apps (موبایل مشتری، داشبورد وب کسب‌وکار V2) │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│  V2 API / Backend                            │
│   - Business Directory Service (Cache از V1) │
│   - Matching/Search Service (AI + Geo)       │
│   - AR Overlay Service                       │
└─────────────────────────────────────────────┘
                    │
         (فقط از طریق Integration Contract)
                    │
┌─────────────────────────────────────────────┐
│  V1 (پروژه‌ی جاری) — منبع حقیقت کسب‌وکار      │
└─────────────────────────────────────────────┘
```

هر سرویس V2 باید مستقل و قابل‌تست باشد؛ Business Directory Service تنها نقطه‌ای است که مجاز به «دانستن» درباره‌ی V1 است — بقیه‌ی سرویس‌ها (تطبیق، نقشه، AR) فقط از طریق همین سرویس داده می‌گیرند، نه مستقیم از V1.

## ۳. داده‌ی جغرافیایی و طبقه (مهم — الزام صریح مالک محصول)

- موقعیت هر کسب‌وکار باید حداقل شامل `latitude`, `longitude`, و (اختیاری ولی توصیه‌شده) `floor_level` باشد.
- **هرگز فقط به GPS برای تعیین طبقه تکیه نکن.** وقتی کاربر ویژگی AR را در یک مکان چندطبقه (پاساژ/مال) فعال می‌کند، سیستم باید صریحاً از کاربر طبقه‌ی فعلی‌اش را بپرسد (یا از یک روش کمکی مثل Wi-Fi/Beacon استفاده کند، اگر بعداً اضافه شد) و نتیجه را با GPS افقی ترکیب کند تا فقط مغازه‌های همان طبقه نمایش داده شوند.
- این باید از همان مدل داده‌ی اولیه‌ی Business Profile (بخش ۲ سند Integration Contract) پشتیبانی شود — یعنی `floor_level` یک فیلد درجه‌یک است، نه یک افزوده‌ی بعدی.

## ۴. اصول عمومی مهندسی (وام‌گرفته از انضباط V1، تطبیق‌یافته)

- **تست واقعی، نه فقط ادعا.** هر قابلیت مهم باید حداقل یک تست یکپارچه‌ی واقعی داشته باشد (نه فقط Unit Test روی منطق ایزوله).
- **حریم خصوصی موقعیت مکانی جدی گرفته شود.** موقعیت زنده‌ی مشتری هرگز نباید بدون رضایت صریح ذخیره یا به کسب‌وکار دیگری فاش شود؛ اصل «حداقل افشا» (Least Disclosure) از V1 اینجا هم برقرار است.
- **صداقت در مستندسازی.** اگر بخشی (مثلاً موتور AR) هنوز پیاده نشده یا فقط Placeholder است، این باید در گزارش‌ها صریح باشد — دقیقاً همان استانداردی که در V1 رعایت شده («هیچ ادعای مبهم مثل "همه‌چیز انجام شد" بدون شاهد»).
- **بدون تصمیم یک‌طرفه‌ی معماری بزرگ بدون ثبت.** اگر موجی به یک نقطه رسید که نیاز به یک انتخاب بزرگ فنی دارد (مثلاً انتخاب فریم‌ورک AR، دیتابیس جغرافیایی، معماری Matching)، باید آن را مستند و به کاربر/مالک محصول گزارش کند، نه فقط ساکت انتخاب کند.

## ۵. پیشنهاد فناوری (نقطه‌ی شروع، نه قفل‌شده)

این‌ها **پیشنهاد** هستند، نه تصمیم قطعی — موجی می‌تواند با استدلال جایگزین کند و باید در اولین گزارش دلیلش را بنویسد:

- **Backend:** یک زبان/فریم‌ورک مدرن با پشتیبانی خوب از Geo-query (مثلاً Node.js/TypeScript + PostgreSQL با پسوند PostGIS برای Query جغرافیایی — هم‌راستا با V1 که از قبل TypeScript/PostgreSQL/Prisma است، برای هم‌زبانی آینده).
- **اپ مشتری:** یک فریم‌ورک موبایل که از دوربین + AR بومی پشتیبانی کند (React Native + ماژول‌های ARKit/ARCore، یا معادل بومی iOS/Android در صورت نیاز به کارایی بالاتر AR).
- **موتور تطبیق نیاز:** یک لایه‌ی جست‌وجوی معنایی (Semantic Search) روی فهرست محصولات/خدمات + فیلتر جغرافیایی — می‌تواند از یک مدل زبانی برای فهم نیت مشتری استفاده کند، اما نتیجه‌ی نهایی باید همیشه قطعی و قابل‌ردیابی به داده‌ی واقعی کسب‌وکار باشد (بدون توهم/اختراع محصول).

## ۶. گزارش‌دهی و هماهنگی

V2 مسیر تحویل و گزارش‌دهی جداگانه‌ی خودش را دارد (نه داخل `AI_HANDOFF/` که مخصوص V1 است) — به `mlino2/HANDOFF/` مراجعه کن. هر تحویل باید شامل باشد: چه‌چیزی ساخته شد، چه تصمیم فنی گرفته شد و چرا، چه چیزی هنوز Placeholder/ناقص است، و آیا به قرارداد یکپارچگی (بخش ۲ سند Integration Contract) نیاز به تغییر داشت یا نه.
